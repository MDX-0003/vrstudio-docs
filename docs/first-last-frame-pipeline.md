# 首尾帧两段式生成方案（图片关键帧 + firstLastFrame）

本文记录"图片模型生成首尾关键帧、视频模型 firstLastFrame 补中间动作"的两段式生成方案：可行性依据、三步管线、每一步的提示词、已知风险、网页验证结果与工具链接入设计。状态：2026-10-20 网页验证通过（用户实测"现在确实成功了"）；工具链接入设计经同日三轮讨论定稿（§8，含素材侧边栏、派生条目与 fullredraw 互斥的路线分流），待按 §8.7 阶段实施。

## 1. 问题来源与思路

`simple_gen_allMediaRef` 的 18 轮迭代暴露了 allMediaRef + 白膜视频的结构性矛盾：白膜视频同时携带位置与动作两种信息，提示词只能声明归属、切不断视觉信号本身，人物动作与移动位置无法同时正确。2026-10-20 用户在 mglc 网页用纯图片（首尾帧截图 + 人物三视图）测试 allMediaRef，结论按原文记录：

> 结果里人物的移动轨迹正确，但纯图片无法约束镜头。

也就是说纯图片参考解决了位置问题，但机位与构图失去锚点。本文的方案把"位置"从参考素材升级为首尾帧契约：视频模型的 firstLastFrame 模式把首图与尾图作为硬边界，中间帧在两端之间补全。镜头由两端同机位的帧钉死，动作只剩中间过程交给文字。

## 2. 可行性依据

- 官方能力：Seedance 2.0/2.5 的 FLF2V（首尾帧生视频）是正式模式，ComfyUI 有官方工作流（见 §9 出处）。即梦的动作控制说明页明确"上传角色姿势作为首尾帧来约束生成动作"。
- 生态实践：第三方有专门的"首尾帧生成器"（用 Seedream 做关键帧再交给视频模型）；社区关键帧制作指南的核心原则与本文管线一致——两张关键帧用同一个图片模型、带同一套角色参考生成，保证两帧之间身份一致。
- 踩坑教训（社区实测，原则采纳、具体数字不采纳）：两帧之间运动幅度过大时中间补间会崩（肢体撕裂、动作跳变）；必要时的解法是加中间过渡帧。CSDN 实战手记里的"垂直位移 12% 熔断"等具体数字只出自该篇付费文，未经复现，不作为参数依据。
- 平台能力（2026-10-20 本机零额度查询）：
  - 图片模型：**专业图片-2.5**（id 44，标签"局部编辑/构图生成"，最多 13 张参考图，比例含 16:9，分辨率 1K/2K/4K，提示词上限 2000 字）；**Seedream 4.5**（id 25，标签"多参考图/系列图模式"，最多 6 张参考图，支持自定义宽高，2K/4K）。两者都适合"场景截图 + 三视图"的多图局部编辑。
  - 视频模型 37（Seedance 2.5）`firstLastFrame`：参考槽位恰好 2 个（首图 + 尾图），时长 4–30 秒，分辨率 480p/720p/1080p，输出比例跟随输入图片（该模式无比例列表）。
  - 图片生成不需要 SD 合规素材登记（CLI 无 asset-id 参数）；视频 firstLastFrame 走网页时不需手动登记。

参考槽位只有 2 个意味着三视图进不了视频步骤——这正是图片步骤存在的理由：外观必须在关键帧里就画成最终角色。

## 3. 管线总览

三步串行，前一步的产物是后一步的输入：

1. **首帧**：`i2_allmedia_first.png`（场景起点图）+ `i1_大臣_三视图.png`（外观）→ 图片模型局部编辑 → 高官坐姿首帧。
2. **尾帧**：`i3_allmedia_last.png`（场景终点图）+ `i1` + **首帧产物**（身份锚点）→ 图片模型局部编辑 → 同一高官站立待命尾帧。
3. **视频**：首帧 + 尾帧 → Seedance 2.5 firstLastFrame，13 秒，文字动作段描述中间过程。

链式生成（首帧产物参与尾帧生成）是身份一致的关键对策：两次独立生成同一角色必然漂移，漂移落到视频里就是人物变形。

## 4. 每一步的提示词

以下提示词按 mglc 网页的图片/视频生成页编写；"图1/图2/图3"按参考图上传顺序指代。已拍板的三个约束贯穿全链：起点画成**真实坐姿**（i2 里下沉示意的白膜翻译成坐姿）、图片步骤**局部换人并去掉 UE 界面**、输出 **16:9**。

### 4.1 步骤一：首帧（坐姿起步）

输入参考图：图1 = `i2_allmedia_first.png`，图2 = `i1_大臣_三视图.png`。候选模型：专业图片-2.5（首选，局部编辑强）或 Seedream 4.5。比例 16:9，分辨率 2K，生成数量 4 挑最佳。

```text
对图1做局部编辑，只改指定区域，其余像素尽量保持。
【替换目标】把图1中偏右、矮案后的白色占位人形替换成图2定义的人物。这个白色人形是下沉摆放的占位模型，它表示"有一位老人坐在这张案后"，不是站立——请画成真实的坐姿：老年男性端坐在矮案后，上身挺直，头与肩露出案沿上方，双手向前自然放在案面上，宽袖垂在案侧，下半身被案面与袍摆完全遮挡。
【人物外观】严格按图2：老年男性古代高官，清瘦，花白长须，黑色高冠与金红绶带，黑底暗红云纹宽袖深衣，腰间革带玉佩，黑色翘头履。只取图2的脸、胡须、冠帽、服装与配色，不取它的背景与站姿。
【位置锁定】人物的左右位置、远近与大小和白色人形一致，头顶不超过白色人形头顶太多，脚部被案遮挡。
【保持不变】机位、构图、透视、宫殿建筑、红毯、矮案与案上器物、背景就座人物、右侧黑袍人物、光照与色温全部保持图1原样。
【界面清理】去掉画面顶部的编辑器工具栏和右下角的界面文字，去掉后按周围画面自然补全；除此之外不新增、不删除任何物体，画面里只能有这位高官一个主角，不能残留白色人形。
【画质】写实古装剧质感，人物光效与场景一致，暗色大厅里脸与长须能辨认。
```

### 4.2 步骤二：尾帧（站立待命，同一人）

输入参考图：图1 = `i3_allmedia_last.png`，图2 = `i1_大臣_三视图.png`，图3 = **步骤一选定的首帧产物**。同一模型、同比例同分辨率。

```text
对图1做局部编辑，只改指定区域，其余像素尽量保持。
【替换目标】把图1中央红毯上的白色占位人形（一个站立的占位模型，只表示位置与大小）替换成人物，画成站立待命姿势：老年男性双脚并拢站在红毯上，双手自然垂在身前，面朝画面右侧的朝堂，身体放松，只有衣料静止。
【人物外观与一致性】人物必须与图2、图3是同一个人：脸型、花白长须、黑色高冠、金红绶带、黑底暗红云纹深衣、革带玉佩完全一致，图3是他在同一场景另一张画面里的样子，以图2和图3共同锁定身份，不得画成另一个人。
【位置锁定】人物的左右位置、远近、大小与脚底落点和白色人形完全一致，站姿高度与白色人形接近。
【保持不变】机位、构图、透视、宫殿建筑、红毯、成排矮案与案上器物、背景就座人物、右侧黑袍人物、光照与色温全部保持图1原样。
【界面清理】去掉画面顶部的编辑器工具栏和右下角的界面文字，去掉后按周围画面自然补全；除此之外不新增、不删除任何物体，画面里只能有这位高官一个主角，不能残留白色人形。
【画质】写实古装剧质感，与图3同一光照与色调。
```

### 4.3 步骤三：视频（firstLastFrame 补中间）

输入：首图 = 步骤一首帧，尾图 = 步骤二尾帧。模型 Seedance 2.5，模式首尾帧生视频，时长 13 秒，分辨率 1080p。

```text
首帧：高官坐在右侧矮案后。尾帧：同一高官站在红毯中央。生成首尾之间 13 秒的连续表演，镜头始终固定，不推拉、不摇移、不切换。
【动作段】按顺序发生：
1. 高官双手撑住案沿，上身前倾，重心前移，收腿站起，靠双手和双腿把身体推起；站直后双手自然下垂贴在身体两侧。
2. 从矮案后沿红毯向尾帧位置连续走 3 到 5 步，右脚先迈出。每一步抬脚离地、脚掌落地、膝盖微屈缓冲；身体随步伐起伏，肩胯反向转动，双臂随腿部自然摆动，宽袖和玉佩流苏滞后摆动。袍摆遮住脚时，靠抬膝、身体起伏和肩胯转动让人看出是在迈步，不能整体平移滑行。
3. 到达尾帧位置后停下，双脚并拢，双手垂在身前，只保留呼吸和衣料余动；到位即停，不再迈步、不再靠近镜头。
【一致性】人物全程与首尾两帧是同一个人，脸、胡须、冠帽、服装与配色不变；第一帧与首图一致，最后一帧与尾图的位置、大小、朝向一致。
【镜头与场景】全程固定机位，宫殿、红毯、矮案、背景人物与光照保持首尾两帧的样子，人物始终沿起终点直线行走，看向前进方向，不要朝镜头走。
【禁止】不出现第二个人物或白色人形；不出现脚底滑行、人物漂浮、肢体撕裂；不出现字幕、水印、Logo。
```

## 5. 已知风险与对策

- **两帧身份漂移**：两次独立生成同一角色必然有差异，漂移进入视频会表现为人物中途变形。对策是 §3 的链式生成（首帧作为尾帧的参考图），且两帧用同一个图片模型。
- **中间补间崩坏**：两帧间运动幅度过大时，中间动作可能撕裂或跳变。本案幅度为中等（坐→起身→走 3–5 步→站定，水平位移约为画面宽度的四分之一），13 秒给了足够过渡时间；若实测崩坏，按顺序尝试：改写动作段放慢节奏 → 缩短时长到 10 秒 → 拆成两段生成后剪辑拼接。
- **白膜残留**：图片步骤是静态问题，肉眼即查、重生成成本低（每步 `--num 4` 挑最佳）；提示词已写"不能残留白色人形"。
- **16:9 裁切**：源截图 1920×1052（1.825:1）出 16:9 需左右各裁约 1.3%；人物与矮案都在画面中部，裁切不伤主体。
- **声音**：没有参考视频，原片原声无法保留；firstLastFrame 的成片声音由模型生成，需要原声时后期回贴。
- **姿势翻译**：i2 里的白膜是唯一的 T-pose 白模被下调高度示意坐姿（用户 2026-10-20 确认），人体结构上不是真坐。首帧提示词已显式把"下沉的占位"翻译成真实坐姿；这是图片模型对小幅度姿势改写的常规能力，但属于本管线里最可能需要多轮重试的一步。

## 6. 网页验证流程

1. 打开 mglc 网页图片生成，选专业图片-2.5，上传 i2 与 i1，粘贴 §4.1 提示词，16:9、2K、数量 4。检查四张候选：坐姿真实（不是蹲站）、案前无白膜残留、顶部工具栏与右下角文字已去除、场景与 i2 一致、人物外观与三视图一致。选最佳存为首帧。
2. 同一模型上传 i3、i1 与首帧产物，粘贴 §4.2 提示词。检查：与首帧是同一人（重点看脸、冠、绶带）、位置大小与 i3 的白膜一致、UI 已去除。选最佳存为尾帧。
3. 打开视频生成，选 Seedance 2.5 的首尾帧模式，上传首帧与尾帧，粘贴 §4.3 提示词，13 秒、1080p。检查：第一帧与最后一帧是否贴合输入、起身自然、行走有真实迈步、镜头全程固定、终点与尾帧一致、无第二人物。
4. 每步失败时只改该步：图片步重试或换 Seedream 4.5；视频步先调动作段措辞，再考虑 §5 的降级顺序。每轮把使用的提示词与结果一起记入台账（后续接入工具链时直接复用）。

## 7. 验收标准

- 首帧/尾帧：人物外观与三视图一致、姿势正确、白膜消失、界面元素消失、场景与源截图一致、16:9。
- 视频：动作顺序完整（起身→迈步→站定）、步态真实（抬脚落脚、无滑行）、镜头固定、首尾帧贴合、13 秒、单人物。
- 整体：肉眼观看不突兀（用户 2026-10-20 拍板的精度标准），位置与动作同时正确。

## 8. 工具链接入设计（2026-10-20 讨论定稿）

### 8.1 决策过程与用户判定

三个候选挂载点（与 gen/patch/fullredraw 同级的新流程；gen 前置可选子页面；gen 新模式内全自动脚本）讨论后的判定：

- 全自动脚本方案出局：图片重绘的"四选一"没有可靠的自动化替代，图片步与视频步各有失败模式，捆绑自动化失去失败隔离。
- 新建同级流程方案方向对但代价重：视频半段与现有 gen 生成页重复；case 模型要为一个 case 内的两阶段产物改 adopt 结构。
- 初版"独立工作台 + 从 patch/fullredraw 进入时新建 gen case"的方案被用户修正，原文记录：

> 我看下来也比较认可你的独立页面，用于同时支持gen的图片模型重绘+patch/fullredraw的抽帧再图片模型重绘，但是你说patch/fullredraw在进入这个独立页面时需要新建case我就觉得有点混乱了，patch/fullredraw本身是自带case的，抽取出来的首尾帧、重绘后的首尾帧能不能作为case自身的素材，和视频、截取区域（patch）、冗余size（fullredraw）一起存放呢？当然在同一个case下分类存放方便审计是有必要的

判定：用户的方案成立且优于"新建 gen case"。原方案把一次任务拆成两个 case，审计线索分裂，成片要从 gen case 的目录回流到原 case 的收尾步骤；这些代价落在用户的每一次操作上，只为省下"assets 通用化"这一次性的契约改动——代价放错了地方。统一 case 的额外收益：同一个 patch case 里可以并存 videoEdit 轮次与 firstLastFrame 轮次（台账按轮次记录模式），直接对比两种生成路线。

第三轮修正确认 fullredraw 与本管线互斥，用户原话：

> 我想了一下，fullredraw和图片模型首尾帧的方案是互斥的，前者作为videoEdit的唯一素材被上传，而后者的核心只是获取两张图片作为原始素材，这一步完全可以在工具外部实现，这就意味着两个流程不可能耦合。只有patch里如拿不到ue内的白膜骨骼动画，才需要考虑使用"白膜示意首尾帧"的方式来重绘动作。而在确定了不存在ue动作的前提情景下，是否做patch的区域切割、视频合并，只取决于我们的"白膜示意首尾帧"究竟是一张完整360视频展开图，还是前者的切割结果。

判定：成立，且理由比"互斥"更根本——冗余带、manifest、recompose 整套机制服务于"以一段视频为结构母版的整幅重绘"；firstLastFrame 不锁定结构、不需要边距，整幅生成即使要修边也只需直接裁切，用不上冗余带机制。两者竞争的是同一职责（决定这个镜头以什么机制被生成），不构成上下游关系。

由此确定的路线分流，总开关是 UE 白膜骨骼动画的可得性：

1. 拿得到 UE 动画：videoEdit 原路线原样成立（patch 区域重绘、fullredraw 整幅重绘），结构锁定继承可信动作反而是优点。
2. 拿不到 UE 动画：走首尾帧管线，按帧的来源分两条。
   - 帧是完整 360 展开图（整幅画面）：走 gen 直接生成，不做区域切割与合并；代价是成片分辨率受 1080p 档限制，整幅展开图的清晰度低于原始全景，按镜头重要性取舍。
   - 帧是区域切割结果：走 patch，区域几何契约（clip.json）+ firstLastFrame 变体生成 + merge 回贴，区域吃满分辨率预算。
3. 取帧本身可以在工具外部完成；工具内的抽帧（从 clip 抽首尾帧）只是便利入口，不是必需环节。

### 8.2 统一模型（五条）

1. **素材列表通用化**：`case.toml` 的 `[[assets]]` 从 gen 专属升级为三条流程通用，但只承载**文件素材**（复制进 case 目录的图片与视频：三视图、抽取的原始帧、重绘定稿帧、用户上传的其他参考）。patch/fullredraw 的既有段（`[source]`、viewport/frames、`*_pad.json` manifest）不动。原始源视频与流程产物不进 `[[assets]]`，作为派生条目展示，见 §8.3。通用化是机制层面的——videoEdit 的 subject_ref 本就是角色矩阵的既有能力，fullredraw 将来可借此挂三视图改善身份漂移；首尾帧管线的接入只连 gen 与 patch（第 2、3 条）。
2. **关键帧工作台是 case 内页面**，入口两个：gen 生成页侧边栏（上传整幅或区域帧 + 三视图）与 patch 生成页侧边栏（提供"从当前 clip 抽首尾帧"的便利按钮）；过程 = 图片模型重绘、每步 4 候选人工挑 1 张；输出 = 写入本 case 素材列表。fullredraw 不接入工作台（互斥判定见 §8.1）。
3. **生成模式变体只加给 patch 与 gen**：patch 的生成从 videoEdit（流程视频为输入）扩展出 firstLastFrame（首尾帧素材为输入），几何以 clip.json viewport 为权威，成片走本 case 既有的 merge 回贴；gen 照旧加 firstLastFrame 模式。fullredraw 保持纯 videoEdit，不增加模式变体。
4. **素材建模用受控角色**（用户已拍板）：定稿帧 `first_frame` / `last_frame`，为补间崩坏预留 `mid_frame`；抽取的原始帧同样入素材列表（角色词表实施时定，语义为工作台输入底图）；三视图沿用 `subject_ref`。firstLastFrame 模式提交时校验恰好一张 first_frame + 一张 last_frame。
5. **提交集是显式选择**：一次生成提交哪些素材由生成页侧边栏的勾选决定（见 §8.4），不再隐式提交全部素材；gen 现行"refs 装入全部素材"的行为随之改为按提交集过滤。

### 8.3 原始视频不进素材列表：派生条目方案

用户提问按原文记录：

> 如果patch/fullredraw也需要有自己的assets列表，那么原始视频本身是不是也需要作为一个asset呢？因为patch/fullredraw可以去截取首尾帧，也可以不去截取，这意味着case下的素材究竟存在哪些，gen用到哪些都是不确定的，后续流程选择素材时，需要按前面提到的分支情况灵活调整可选项。

判定：原始视频**不作为 `[[assets]]` 条目**，理由三条：

1. `[source]` 是 patch/fullredraw 的身份与几何契约锚：check_source 用哈希守卫"换源 = 新 case"，merge 还要回读源视频贴回。`[[assets]]` 是可自由增删的 mglc 参考清单。两者生命周期与语义都不同，塞进同一列表会造出指向同一文件的双重真源，与"唯一权威点"的工作区原则冲突。
2. patch/fullredraw 真正提交给 mglc 的视频从来不是原始源，而是流程产物（clip / pad 产物），它们由流程状态派生（`[extract] current` 指针、manifest），同样不应手工增删。
3. gen 流程里视频确实就是素材，那是 gen 没有 `[source]` 契约锚的结果，不代表 patch/fullredraw 要向它看齐。

解决方式：源视频与流程产物在侧边栏作为**派生条目**只读展示——不复制文件、不进 `[[assets]]`、不可增删，标注其在各模式下的提交行为（videoEdit 自动以流程视频为输入，无需勾选）。fullredraw 的源视频与 pad 产物同样作为派生条目展示，但其侧边栏不出现工作台入口与 firstLastFrame 模式（互斥）。派生条目将来可勾选提交（例如 allMediaRef 拿 clip 当 space_ref 复现旧工作流）留作扩展位，首期不实现。

用户提出的"不确定原则"收录为本设计原则：case 的素材清单是动态事实集合（抽没抽帧、重绘没重绘取决于用户走的分支），哪些素材参与生成是每次提交的显式选择；侧边栏的可选项与校验按"当前生成模式 × 流程阶段"动态调整。

### 8.4 生成页素材侧边栏（UI 设计）

用户方案按原文记录：

> 把现有的、纯gen mode下的素材界面合并到gen页面的一个可展开侧边栏，支持选取若干项作为提交给mglc的素材，并且每次修改选择都能够自动修改提示词模板里的key-value对，value可以实时填

设计展开：

- **位置与形态**：三流程的生成步骤页统一挂可展开侧边栏；gen 向导原"素材"独立步骤并入侧边栏（`docs/multi-asset-plan.md` §4.2 的素材步骤设计演进为本设计），patch/fullredraw 由此获得素材管理能力。
- **两个区块**：「流程产物（派生 · 只读）」列源视频与当前 clip / pad 产物；「文件素材（`[[assets]]`）」列三视图、抽取原始帧、重绘定稿帧等，支持增删、角色、排序。
- **提交集勾选与模式感知校验**：勾选若干文件素材作为本次提交。可选项与错误提示按模式动态调整——videoEdit 不需要勾选（自动用流程视频），fullredraw 的生成页只有 videoEdit 一种模式、可选素材仅 subject_ref 类、无工作台入口；firstLastFrame 要求恰好 1 张 first_frame + 1 张 last_frame，工作台输入用的原始帧与三视图默认不可选入；allMediaRef 按角色矩阵校验。前端校验只做引导，权威校验仍在 vrgen 提交前执行（沿用 multi-asset-plan 的"校验只在 vrgen"原则）。
- **提示词联动**：勾选变化时重算 asset_list，把素材变量值里的 `@VideoN` / `@ImageN` 标记按旧编号到新编号的映射自动改写，并实时预览渲染后的完整提示词；变量值可在侧边栏与提示词面板实时填写（复用 prompt show/save 草稿机制）。引用了已被移除素材的标记不自动删除，标红警告由用户处理。
- **持久化**：提交集（选中素材 id 与角色覆盖）作为 job 级生成参数草稿持久化，与 generation.toml 同级，字段实施时定；未显式选择时按模式取默认集（firstLastFrame 默认选最新定稿的一对帧）。vrstudio 侧生成时只把勾选素材写进 refs JSON——refs JSON 本就支持任意子集，vrgen 无需改动。

### 8.5 已识别的实施隐患：成片与几何契约的对齐

videoEdit 时代的成片跟随输入视频几何，merge 按此假设回贴；firstLastFrame 的成片比例跟随首尾图、分辨率为 480p/720p/1080p 档，与 clip 画布可能不一致（例如 clip 1920×1052 对 1080p 档 1920×1080）。对策从源头做起，用户已同意按原文记录（"截取图片的分辨率始终按原始视频的分辨率，这点我是同意的"）：

- 抽取的原始帧始终按被抽帧视频的原始分辨率导出（patch 的 clip 分辨率；工具外部取帧同理按其源视频分辨率），不预缩放。
- 工作台输出的定稿帧按几何出图：patch 按本 case 的 clip 契约裁切或定制宽高，使成片与契约的偏差只剩分辨率档位差，由 merge 既有的归一逻辑处理；gen 整幅帧没有外部几何契约，按帧自身比例出图，成片分辨率受档位限制——整幅 360 展开图的清晰度取舍已在 §8.1 路线分流中记录。

实施前需检查 merge 对"结果尺寸 ≠ clip 尺寸"的现有行为并补测试。

### 8.6 契约变更清单（按 AGENTS 硬规则 1，先改 docs/case-model.md）

- `[[assets]]` 通用化（三流程）与角色词表扩展（first_frame / last_frame / mid_frame / 原始帧角色）；源视频与流程产物保持派生，不进 assets。
- 提交集草稿字段进 job 级生成参数；gen 提交行为从"全部素材"改为"提交集过滤"（仅 vrstudio 侧变化）。
- firstLastFrame 模式进 MODE_ROLES：恰好 2 张图片（首+尾）、无视频；时长为 CLI 参数（前端 4–30s 下拉，显式值 > 最长视频时长 > 纯图片默认 4，见 firstlast-dev-plan.md WP0）。
- vrgen 新增图片生成任务类型：进台账、走项目会话额度；图片模型无需 SD 合规登记，视频 firstLastFrame 的首尾图是否需要登记在 CLI 侧待验证。
- 时长不做 generation.toml 持久化；`--duration` 是唯一入口（用户 2026-10-20 拍板："默认4，有视频就设置成视频长度max"），解析顺序为显式值 > 最长视频时长 > 4，显式值按模式 duration 范围校验。
- vrstudio generate 为 patch 增加走 `--refs` 的提交分支（现仅 gen 走 refs；fullredraw 不加，互斥）。

### 8.7 实施阶段建议

1. vrgen 后端先行：firstLastFrame 模式、图片任务类型、duration 持久化（不依赖 web，可用 CLI 验证）。
2. case 模型：assets 通用化与角色词表（两侧镜像同步）。
3. web：gen 与 patch 生成页素材侧边栏（含提交集与提示词联动）、关键帧工作台（gen 上传入口 + patch 抽帧便利入口）、patch 的 firstLastFrame 模式变体。
4. 几何对齐：抽帧按原始分辨率导出；工作台出图按 case 几何裁切；merge/recompose 对非匹配尺寸成片的行为检查与测试。
