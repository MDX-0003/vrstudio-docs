## 1. 结论先行

前端层选用 **Vue 3 + TypeScript + Vite + Element Plus** 重建界面，旧前端保留在 `/`，新前端挂在 `/next`，按页面迁移、功能对齐后切换默认入口。

- 被替换的是"浏览器里负责画界面的那一层"：两个 HTML 模板、6 个 partial、10 个静态脚本里除 WebGL 与拖框数学之外的绘制与状态部分、两份内联 CSS。
- 不被替换的是"把数据与文件送到浏览器门口的那一层"与"真正干活的 Python 与命令行"：Starlette 路由、Jinja2、`tasks.py` 队列、`app.py` 业务、`erp360.js` 的 WebGL 投影与双路同步、`pick.js` 的拖框坐标计算、`docs/case-model.md` 的 CLI 契约。
- 后端需要同步补齐的五件事：身份与 case 归属、任务按人隔离、浏览器上传、并发写入的版本检查、扣费归属。这五件事不做，换任何前端都撑不住局域网多人使用。

上述结论已于 2026-10-23 由用户确认。确认时补充两条约束：账号与密码暂缓，先保证局域网内多人分别访问各自 case 的应用场景跑通；任务并发先用单队列。身份与队列都必须预留扩展接口，后续换账号体系或多 worker 时页面与接口不变。

## 5. 关键分歧与判断

### npm 是否等于前后端分离

用户的原话：

> 我对前端几种技术方案的了解、代价、适合场景了解不多，不过我见过的一些成熟开源项目都使用的是npm，是不是对应着你说的选项3？

判定：该复述不成立，其中的等号不成立，但观察本身是对的。

- **成立的部分**：成熟开源项目确实普遍使用 npm。npm 是 JavaScript 的包管理器，负责下载依赖与锁定版本。
- **不成立的部分**：npm 不等于前后端分离。npm 是否对应方案 3，取决于装了 npm 之后拿它做什么。只用 npm 安装代码检查、格式化或开发服务器，项目仍然可以是服务端渲染的小工具；装上 Vue 或 React 并让浏览器接管整页渲染，才是方案 3 的完整形态。
- **修正**：判断方案时看三个问题，不看是否用了 npm。第一，页面由谁渲染，是服务端返回完整 HTML，还是浏览器接管整页。第二，状态住在哪里，是服务端为唯一事实来源，还是浏览器里也有一份长期状态。第三，后端出什么，是 HTML 片段还是 JSON 数据。

### 现在的项目是否属于前后端分离

判定：已经属于"后端出 JSON、浏览器画界面"这条路，只是缺了前端工程这一半。

- 证据一：前端 100% 用 `fetch` 加 JSON 取数据，没有任何 `<form>` 提交（现状画像 §5）。
- 证据二：Jinja2 只渲染 `name` 与 `flow` 两个变量（`app.py:189-190`），其余内容全由 JavaScript 画出（现状画像 §5）。
- 证据二在 2026-10-23 写本文时重新打开 `wizard.html` 核对：模板里只有 `<title>{{ name }} · {{ flow }} · vrstudio</title>`、`<body data-name="…" data-flow="…">`（`wizard.html:5,193`）、以及 `{% if flow == "patch" %}` 一处条件（`wizard.html:250-256`），与画像一致。
- 结论：不需要在"服务端渲染还是浏览器渲染"之间再做选择，这个选择已由现有代码做过。选型工作只是把浏览器那一半换成更结实的写法。

### 是否选用前后端分离

判定：选。理由不是"交互天花板高"，而是用户选了"先解决改不动"。

- 现状"改不动"的根因是缺少组件边界与类型约束，不是缺少 CSS。HTMX 一类方案能减少手写 JavaScript，但不建立组件边界与类型约束，"改不动"的根因不会消失。
- 用户要求"套用成熟设计系统"，成熟设计系统都以组件库形式提供，组件库依附于渲染框架。
- 用户要求"新旧并行再切换"，需要一条能按页面迁移的边界，独立的前端工程天然提供这条边界。

### 是否继续纯原生 JavaScript

判定：不继续作为主路线，但不全盘否定。

- 不继续的理由：现状约 2845 行脚本（现状画像 §4），10 个文件共享 `CASE`、`FLOW`、`info`、`$` 等全局变量，加载顺序硬编码在 `wizard.html:324-333`，新增模块要同时改脚本顺序与 `renderAll` 的字符串注册表（`common.js:37-44`）。这些约束不随换一套 CSS 消失。
- 不全盘否定的地方：`erp360.js` 的 WebGL 着色器与双路同步、`pick.js` 的拖框坐标计算保留原代码，只包一层组件。

### 是否选用全栈框架

判定：不选 Next.js 或 Nuxt。

- 页面在局域网内登录后使用，没有搜索引擎收录与公开首屏需求，服务端渲染换不到实际收益。
- 引入 Node 运行时与一整套框架约定，增加部署、调试与升级的复杂度。

### 是否选用桌面壳

判定：不选 Electron 或 Tauri。

- 工具已通过浏览器访问，多人还要共用一台机器，桌面壳只增加安装、更新与分发成本。

### 是否选用本地优先数据库

判定：不选。

- 权威数据在服务端文件与 vrgen 记录里，不需要离线编辑与多端同步。

### 选择 Vue 还是 React

判定：Vue 3。

- 阅读成本低：单文件组件把模板、逻辑、样式放在一处，Python 开发者读起来接近 HTML；React 的 JSX、hooks 与状态副作用分离需要多一层理解。
- 状态模型贴合现状：现有全局 `info` 可以收敛成一个 Pinia store。
- 用户正在从零建立前端认知，工具越少，学习成本和项目复杂度的交叉点越靠前。
- 让步：如果用户日后更看重设计系统完成度，React + Ant Design 6 是并列备选，但两者只能选一个，不能在同一个项目里混用两套渲染框架。

### 选择 Element Plus 还是 Ant Design

判定：Element Plus。判断依据按权重排序如下。

1. **维护活跃度**：Element Plus 的正式版是 2.14.7，2026-09-30 发布，2026 年内按月或按周持续发布；Ant Design 的 React 版是 6.6.5，2026-09-20 发布；Ant Design Vue 的正式版停在 4.2.6，2024-11-11 发布，近两年没有新正式版。
2. **深度依赖的组件是否齐全**：上传（拖拽、进度、失败重试、多文件、分片）、表格（列配置、行选择、虚拟滚动）、抽屉与对话框、步骤条、表单校验、可自动增高的长文本输入。Element Plus 与 Ant Design 都齐全。
3. **主题令牌能否落地**：Element Plus 用 SCSS 变量加 CSS 变量重构了几乎所有组件的样式系统，支持在 `:root` 块里改主色、字号、圆角，支持暗色模式与密度调整。
4. **文档与语料量**：两者中文资料都充足，Element Plus 的组件命名与中文文档更贴近后台管理类的使用习惯。
5. **体积与性能**：在局域网 2–5 人的场景下几乎不考虑，且有按需引入。
6. **与 Vue 的契合度**：Element Plus 是纯 Vue 原生设计，Ant Design Vue 是照搬 React 版的设计，在 Vue 里写会多一层理解与转换成本。

排除 Ant Design Vue 的直接理由只有一条：第 1 条不满足。它并不差，但新项目建立在近两年没有正式发布的库上，后续每个缺陷都只能等对方发布新版本。

### 是否选用 TypeScript

判定：选用。

- 用户提问"不太理解 TypeScript 的作用，以及它为什么在目前流程里没有要取代的对象"。答案见 §9。
- 它值得选的理由：现状约 2845 行前端脚本，接口有 28 条，并且已经有"两种响应契约并存"的隐式约定；用户加 AI 协作、半年内还会有同事上手，类型检查把"改后端导致前端悄悄坏掉"变成"改代码时就报错"。

### 是否选用 JSDoc 注释替代 TypeScript

判定：不用 JSDoc 替代。

- JSDoc 加 `// @ts-check` 能在不改扩展名的前提下获得大部分类型检查，代价是组件文件格式受限，组件库的类型集成也不完整。
- 项目已经有构建步骤，额外获得 TypeScript 的完整能力没有新增工具链成本，因此直接上 TypeScript。

### 选择构建工具

判定：Vite。

- 现在改前端不需要重启服务，`StaticFiles` 每次请求都从磁盘读文件（现状画像 §8），但脚本版本号要人工维护 `?v=N`（`wizard.html:324-333`，v=1/4/5/3/6/3/3/2/12；`cases.html:61` v=1），改了脚本忘改版本号时浏览器会继续用旧缓存，表现为"改了没反应"。
- Vite 用内容指纹生成文件名，浏览器按内容而不是按手工编号取缓存；开发时改一行代码，页面一秒内自动更新。

## 6. 现有前端的运行原理

这一节用用户能核对的方式回答"现在的网页是怎么画出来的"。路径以 `E:\VRAIGC\vrstudio\src\vrstudio\web` 为根，行号取自现状画像，写本文时抽查了 `common.js` 与 `wizard.html` 的对应位置。

一次"按一下鼠标到画面变化"的完整链路分十三步。

1. 用户在命令行执行 `uv run vrstudio serve`，uvicorn 在指定端口开启 Web 服务（`cli/serve.py:27-45`）。
2. 浏览器请求 `http://localhost:8760/case/dacne`。
3. uvicorn 收到请求，把 HTTP 报文解析成 Python 能处理的调用。
4. `app.py` 的路由表（`app.py:2144-2185`）匹配到 `GET /case/{name}`，用 Jinja2 把 `wizard.html` 渲染成 HTML，只替换 `name` 与 `flow` 两个位置（`app.py:179-190`）。
5. 浏览器收到 HTML，按 `wizard.html:324-333` 的顺序下载并执行十个脚本。
6. 脚本启动后发出 `GET /api/case/dacne`，取回整份 `info`（约 36KB）。
7. 脚本用这份 JSON 在页面的空壳面板里画出素材行、提示词卡片、候选图与提交条。
8. 用户按下鼠标，事件在浏览器内部产生，此时还没有发出任何请求。
9. 对应的 `onclick` 处理器被调用，拼出 JSON 并调用 `post()`（`common.js:46-64`）。
10. 请求到达 uvicorn，路由匹配到 `api_inner`（`app.py:1864-1881`），改写草稿文件，算出轻量 JSON 应答。
11. uvicorn 把结果序列化成 HTTP 响应发回。
12. `post()` 拿回 JSON，执行 `info = d`，再调用 `renderAll()`（`common.js:56-63`），十二个渲染函数全部重跑。
13. 预览图地址变化后，浏览器再去 `GET /img/dacne/vp.png?frame=N` 取图，新图到达后画面更新。

链路中有三点容易被混为一谈，分开说明。

- **返回 HTML 只发生一次**：即第 4 步；此后整页 HTML 不再变化。
- **返回静态文件**：`.js` 与预览图由 Starlette 直接从磁盘发出，不经过业务代码。
- **返回 JSON**：交互的全部动作都走这条，包括改素材角色、改提示词、提交任务、查任务状态。

另外要澄清一处层次差异：选区点击本身不启动命令行子进程，只有 `POST /api/case/{name}/run`（`app.py:2000-2013`）会把任务交给队列，由队列在另一个进程中运行 `python -m vrstudio ...`（`tasks.py:105-133`）。几何点击走轻量接口是为了避免每次点击重扫 4K 素材（`frontend-decisions.md` 第 10 条）。

### 一次数据改动为什么会重画全部界面

`common.js:56-62` 的实际代码如下（写本文时重新打开核对，与画像描述一致）。

```js
const prev = info;
info = d;                                   // 这些端点都回新 info
// draft/nudge 等高频端点不回 prompt / 生成参数；保留上一份，避免面板被清空。
if (!info.generation_params && prev && prev.generation_params)
  info.generation_params = prev.generation_params;
if (!info.prompt && prev && prev.prompt) info.prompt = prev.prompt;
renderAll();
```

`renderAll()` 依次调用 `renderSteps`、`renderAssets`、`renderPick`、`renderExtract`、`renderResultStrip`、`renderGenParams`、`renderSubmitBar`、`renderFinish`、`renderStepFiles`、`renderPrompt`、`renderCompare`、`renderKeyframe` 十二个函数，未加载的函数按名字跳过（`common.js:37-44`）。

因此"改一个素材角色会重跑全部渲染"这件事在设计时是有意为之：每个渲染函数都要能独立重跑，代价是每次改动都重画全部区域。换成组件化之后，"数据一变只更新读了它的组件"由框架负责，不再需要这份注册表。

## 7. uvicorn、端口与进程的复述与判定

用户的原话：

> uvicorn 是什么？在某个端口开一个web服务，我可理解为是一个本地进程，走系统级别的端口+http协议的传输规范，在本地多进程之间做信息交换吗？比如点击事件的发送、后端cli命令的触发？所以我们目前的serve服务就是不断地做"监听端口 - 返回html信息给浏览器"来实现的网页渲染？

逐句对照如下。

- **"uvicorn 是一个本地进程"**：成立。它在命令行启动后常驻。
- **"走系统级别的端口加 HTTP 协议的传输规范"**：成立，但要分清两层。端口属于操作系统，它把发往某个数字的消息引到那个进程；HTTP 是跑在端口之上的一套消息格式，规定请求与响应长什么样。uvicorn 是理解这套格式、并替你调用 Python 代码的那一层。
- **"在本地多进程之间做信息交换"**：不成立。浏览器不是 uvicorn 派生出来的兄弟进程，它是独立的程序，可以跑在另一台机器上，多人部署时正是如此；它和 uvicorn 之间只靠"连到这个端口、按 HTTP 说话"这一种方式交换信息，没有共享内存，也没有直接调用。
- **"点击事件的发送、后端 CLI 命令的触发"**：层次不同。点击事件在浏览器内部处理，浏览器只在需要时按 HTTP 发一条请求；后端收到请求后，才可能在进程里再启动一个命令行子进程。这是"发起子进程"，不是"与浏览器做多进程通信"。
- **"serve 服务不断监听端口、返回 HTML 给浏览器来实现渲染"**：方向成立，但不完整。服务同时返回三种东西：HTML 空壳、静态文件、JSON 数据。绝大多数交互发生在第三种上，返回的不是 HTML 而是 JSON；HTML 只在第一次打开页面时返回一次。

### TypeScript 是什么，以及它为什么没有要取代的对象

用户的原话：

> 我主要不太理解TypeScript 的作用，以及它为什么在目前流程里没有要取代的对象？

解释要点。

- **它是什么**：TypeScript 是 JavaScript 加一层"数据长什么样"的声明，这层声明在运行前被检查，运行前就被擦掉，运行时不产生任何代码。它标注的是数据形状，不是语法。
- **它解决的问题恰好是项目里已存在的缺陷**：现状画像 §5 指出"两种响应契约并存，是隐式约定"，`common.js:58-61` 靠"看见 `viewport` 就认定是精简版"来打补丁。这段代码没有错，但依赖猜字段；后端改了字段名，补丁悄悄失效，表现为某些区域不刷新，不会报错。用 TypeScript，这层约定变成 `interface` 加类型收窄函数，后端改字段时构建阶段就报错。
- **它在用户这种协作模式下额外值钱**：代码会由用户本人、AI 协作者与半年内加入的同事先后修改。AI 调用不存在的字段时构建阶段就被拦住；同事读 `interface CaseInfo` 就知道接口返回什么，不用去读 `app.py:966-1002` 反推；改一个字段名时所有用到的地方一起标红。
- **为什么在流程里没有要取代的对象**：因为旧代码里没有"类型检查"这件事，没有东西可被替换，只能说是"在原来空白的位置补上一件事"。但旧代码里确实有非正式的类型约定，即 `app.py:966-1002` 的字段清单、`docs/case-model.md` 的契约文字、`common.js:58-61` 的猜字段规则；TypeScript 是把这三样替换成代码里的 `interface` 与自动检查。
- **代价**：需要多写一些声明，部分现在能跑的写法需要加类型标注；"泛型"与"类型收窄"这类概念在复杂场景才出现，日常写的类型多为 `string`、`number` 与 `interface`。
- **不值得用的条件**：项目只有几百行脚本、只有一个人写、接口只有两三个、三个月内会废弃。本项目的条件与此相反。

### 流程图里可以多选的三处

讨论中画了图三，标出三个存在多个合格候选的位置，并说明为什么每次只能选一个。

- **框架层**：Vue 3 与 React 都能替换手写 JavaScript 的绘制逻辑。同一个项目只能选一个，因为两套渲染机制会同时维护两份状态模型。
- **类型层**：TypeScript 是主流选择；JSDoc 注释加 `// @ts-check` 是轻量替代。选 JSDoc 的代价是组件文件格式受限，组件库的类型集成不完整。
- **构建层与控件层**：Vite 几乎是 Vue 项目的默认选择；控件库 Element Plus 与 Ant Design 二选一。

### 组件库的选择标准

用户提问"组件库的选择有什么讲究／选择标准呢"，讨论给出的六条标准按本项目权重排序如下。

1. **维护活跃度**：看最近一次正式发布的版本与日期、去年一年发布了几次、有没有长期未合并的关键缺陷修复。不看 star 数。
2. **深度依赖的组件是否齐全**：上传、表格、抽屉与对话框、步骤条、表单与校验、可自动增高的长文本区域。
3. **主题定制能否落到令牌**：能否用 CSS 变量覆盖主色、字号、圆角，是否支持暗色模式与密度调整。
4. **文档与语料可用度**：中文文档是否完整、示例是否可运行、社区问答的数量与质量。这一条直接影响用户与 AI 协作者查资料的效率。
5. **体积与性能**：在局域网 2–5 人、页面要加载 4K 视频与预览图的场景下，权重很低。
6. **与 Vue 的契合度**：纯 Vue 原生设计优于照搬 React 版的设计。

讨论同时列出五个常见的选型陷阱：被演示站的默认外观误导、同时引入两个组件库、把控件库当成设计系统、忽略升级路径、只看文档片段不看示例是否可运行。

### 设计令牌

用户的原话：

> 设计令牌这个单词我有点难以理解，但是我现在可以理解为"组件库Element Plus"的全局规范属性，有点像代码的"超参数"

判定：方向成立，归属对象与生效机制两处需要精确化。

- **成立的部分**：设计令牌确实是一组全局的规范属性，改动一处、所有依赖它的地方一起变。把"超参数"用于理解它是合适的：超参数是训练前就定好、会影响整体行为的量；设计令牌是页面搭起来之前就定好、会影响所有控件外观的值。
- **不成立的部分一（归属）**：设计令牌不只属于 Element Plus。它包含两部分的合并结果：第一部分是项目自己定下的 4 到 6 个颜色、字号阶梯、间距台阶与统一圆角，这一部分由项目决定，与用哪个控件库无关；第二部分是 Element Plus 自己的一套默认令牌，即它的主色、字号、圆角、间距、阴影值。项目要做的是用第一部分的取值去覆盖第二部分的默认值，而不是把设计令牌理解成"组件库自带的东西"。
- **不成立的部分二（生效机制）**：超参数在训练开始前设定，训练中通常不再改变，改了要重训；设计令牌是运行时的 CSS 变量，改一个值在任何时候都立即生效，不需要重新构建一整套页面。它更像配置文件中的全局默认项，而不是一次性的实验设定。
- **与"不好看"的关系**：只装 Element Plus 不定令牌，页面会获得统一但普通的后台观感；令牌决定这个工具自己的观感。

设计令牌具体包含哪些项、怎样覆盖 Element Plus 的默认变量，属于实施细节，不在本文展开，按 §12 第 5 项另起方案文档时写。

### 其他已澄清的小概念

讨论中还澄清了四个用户未直接提问、但容易混淆的概念，记在这里。

- **npm**：JavaScript 的包管理器，只负责下载依赖与锁定版本，不决定页面由谁渲染。
- **Vite**：构建工具，把 TypeScript 与 `.vue` 文件翻译成浏览器能执行的普通 JS 与 CSS，产物由 Starlette 当作静态文件发出。
- **Pinia**：Vue 的状态管理配套工具，对应现有的全局 `info`；不是必装项。
- **Vue Router**：Vue 的路由配套工具，让地址栏反映当前步骤，对应现有的 `curStep` 内存变量与 `showStep()`；不是必装项。

## 13. 需求理清方法

需求还停留在感受层面时，先把它变成可判断、可验收的东西。下面六步按顺序执行。

1. **写角色与场景，不写功能名。** 不要写“需要上传功能”，要写“同事在自己的 Windows 电脑上，通过局域网浏览器，把一段 4K 视频建成 case 并提交预演”。角色、设备、网络、权限与时间限制写出来，功能会自然浮现。
2. **写任务卡，并补失败路径。** 统一用“当……我想……以便……”的句式。每个任务再补三条失败路径：中断、权限不足、状态被别人改过。失败路径往往比正常路径更能决定界面结构。
3. **写约束卡。** 约束卡写部署环境、文件体积、并发人数、额度归属、网络条件与必须保留的旧能力。约束会直接淘汰方案，比讨论喜好有效。
4. **把“好看”“流畅”换成可观测行为。** “页面好看”改成“每页第一眼能看到一个主行动，正文行长不超过 80 个字符，同类控件圆角与间距一致”；“内容好读”改成“提示词默认只显示摘要，展开后左侧正文、右侧变量，长文件名换行不撑破布局”；“流程好用”改成“刷新页面回到同一步，保存后 1 秒内出现已保存提示，提交前能看到本次扣哪个项目与会话的额度”；“改得动”改成“新增一个步骤只改路由表与一个页面组件，新增一个接口只改接口客户端与类型定义”。
5. **分成三栏。** 把需求分成“现在必须做”“以后可以做”“明确不做”三栏。第三栏最重要，它防止方案越做越大。按当前信息，现在必须做的是新前端壳、case 列表、生成页、上传、任务中心、身份与归属、设计令牌；以后可以做的是暗色模式、移动端适配、快捷键全集、操作记录查询、按人任务队列；明确不做的是公开注册、跨公网部署、离线编辑、多人同时编辑同一 case、桌面客户端。
6. **用原型做对比实验。** 一次只验证一个变量。例如同一张生成页做两个版本，一个把提示词放主区，一个把提示词收进抽屉，让真实内容跑一遍，记录完成“改提示词并提交”的时间与出错次数。原型验证过的结论，比讨论十轮都可靠。每轮结论按 `frontend-decisions.md` 的六段格式记录：问题、决策、排除的方案、验证、涉及文件、后续入口。

**三个问题可以筛掉伪需求。**

- 这个操作每周发生几次？低频操作不值得做专用界面，用命令行或手工步骤更便宜。
- 它是否改变数据所有权或对外契约？改变就要先在 `docs/` 立项，不能顺手加。
- 不做它，哪条验收过不了？答不出来就不做。

**判断一个方案按三步走。**

1. 先看约束：部署环境、并发人数、文件体积、必须保留的能力。
2. 再看交互复杂度：以增删改查为主，还是以拖拽、画布、实时状态为主。
3. 最后看团队维护能力：谁能读懂、谁能改、出了问题谁能定位。

不要从“哪个框架最火”开始。框架热度不回答上面任何一个问题。

## 14. 前端设计 skill 调研

官方来源是 Anthropic 的 `frontend-design` skill。它要求代理以设计负责人身份先写一份简短设计计划，包含 4 到 6 个命名颜色、字体角色、布局概念与 ASCII 线框，对照需求复查后才写代码；它还列出要避开的模板化默认，例如暖奶油底加衬线标题加陶土色、近黑底加单一荧光色、所有内容切成同样圆角卡片。

这个 skill 的流程适合 Phase 0，但它面向有独特视觉识别的展示页，不完全适合高密度内部工具。可以借用的是“先写计划再写代码”“克制装饰”“文案用主动语态”“空态与错误要给方向”；不要照搬它的“大胆审美”要求。

社区还有多套前端 skill：`uiux-storybook-architect` 用访谈方式先确定用户、任务与内容，再产出设计故事书并检查 WCAG 2.2 AA；`gral-frontend-skill` 覆盖字体、布局、OKLCH 配色、动效与可访问性审查；Addy Osmani 的 Web Quality Skills 关注性能、可访问性与最佳实践。不要一次装五套，它们的规则会互相冲突；选一套主 skill 加一套可访问性审查就够。

本项目的建议是 Phase 0 用 Anthropic 的 `frontend-design` 流程产出设计计划，再用浏览器截图做视觉验收；不把几十个社区 skill 全装进项目。
