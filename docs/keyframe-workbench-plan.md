# 首尾帧重绘工作台方案（patch 图片重绘 + firstLastFrame）

状态：patch 部分已实施（2026-10-22）；WP0–WP3 与测试已落地，gen 入口与真实提交待接（见 §10）。本文不改变 `firstLastFrame` 的生成语义，只重做 patch 的图片重绘工作台、素材库与提交集的边界、提示词复用与两帧到视频的交接。

> 2026-10-26 修订：图片步输入由「固定三张」改为「有序参考图清单」，`keyframe.toml` 的 `sheet` 升级为 `refs`，支持一张人物三视图加任意细节图。方案见 `docs/plan/asset-library-separation-plan.md`；本文 §2.3、§4.3、§5.2–5.3 的固定输入描述以新方案为准，保留原文作为历史记录。

## 1. 需求与现状

### 1.1 用户描述（原文）

用户在 2026-10-22 的对话里这样描述芒果灵创网页上的执行过程：

> 在给定了一个视频（里面只有白膜的简单移动动画，不存在正确的过渡）后，我需要截取出里面动画开始的首帧和尾帧（流程里会把首帧-尾帧中间全部视频部分进行替换）这一步目前patch流程的第一步已经可以做到了，我也能在[E:\VRAIGC\vrstudio\cases\walk_02\extracts\20261022-164714]下看见图片文件，但是我在前端的”生成“页是没有办法直观地看到这两个即将被我重绘的”首尾帧图片“的。接下来我需要将首帧原始图+人物三视图提交到芒果灵创的图片模型，并按提示词生成首帧重绘，然后将尾帧原始图+人物三视图+首帧重绘图再次提交到芒果灵创的图片模型，再次按新的提示词生成尾帧重绘。最后我拿到首尾帧重绘图，只提交这两张图片给芒果灵创的seedance - firstlastframe模式，再次使用提示词生成新的完整视频片段。这中间涉及了三段不同的提示词，我希望至少生成图片这部分，有办法复用一些提示词的框架，甚至有办法一键完成两次图片生成模型的请求提交和结果回收。

同一轮对话里用户还提出两件事：把生成页里现在叫「关键帧工作台（首帧 / 尾帧重绘）」的区域改名；这个平台面向非技术背景用户，前端操作步骤要简化。

### 1.2 现有实现已经具备的部分

- patch 的 `extract` 在写完 `clip.mp4` 后直接导出 `first_frame_raw.png` 与 `last_frame_raw.png`，不缩放，与 clip 同目录（`vrstudio/src/vrstudio/cli/extract.py:69`、`:131`）。walk_02 的当前版本里这两个文件存在，尺寸 1920×1080。
- 服务端已经把两张原始帧连同缩略图地址返回给页面：`_raw_frames()` 产出 `{id, role, label, path, exists, url}`（`vrstudio/src/vrstudio/web/app.py:527`），并挂在 case 信息的 `raw_frames` 字段上（`app.py:832`）；`/img/asset/<case>/first_raw` 与 `/last_raw` 由同一路径解析（`app.py:1052`）。
- 图片生成任务已经是一条完整的台账生命周期：提交、轮询、下载全部候选、逐张闸门、写 `run.json` 的 `results`（`vrgen/src/vrgen/round/image.py`）。CLI 入口是 `vrgen image submit`，参数含 `--image`（可重复）、`--ratio`、`--resolution 1K/2K/4K`、`--num 1..4`、`--session-id`（`vrgen/src/vrgen/cli.py:335`）。
- firstLastFrame 模式、恰好一对首尾帧的提交校验、非 16:9 拒绝、merge 比例校验都已实现（`vrstudio/src/vrstudio/cli/generate.py:296`、`app.py:944`）。
- 工作台页面骨架已经存在：折叠区、步骤下拉、候选网格、挑选写素材（`vrstudio/src/vrstudio/web/templates/partials/generate.html:5`、`static/keyframe.js`）。

### 1.3 读代码确认的五个缺口

1. **两张原始帧只渲染成复选框文字，没有画成图片。** `renderKeyframe()` 用 `addRow()` 为每张原始帧生成一个复选框标签，`raw_frames[].url` 从未写进 `<img>`（`static/keyframe.js:74-90`）。数据是齐的，缺的只是渲染。
2. **图片步提示词写死在大臣剧情上。** `KF_PROMPTS` 是两段固定文本，内容分别写死了「矮案」「红毯」「黑袍人物」「高官」（`static/keyframe.js:10-40`）。换一个 case 后这段提示词仍然出现，既不能复用，也会误导用户。
3. **图片任务没有走项目会话。** `_keyframe_argv()` 只组装 `--job/--prompt/--image/--ratio/--model-id/--resolution/--num/--workdir`，没有 `--session-id`（`app.py:1198-1209`）。vrgen 在该参数缺省时取配置的 `mglc.session_id`，缺省为 0，也就是个人额度；用户在决策 22 里已经记录个人额度为 0，所以真实图片提交会失败。
4. **尾帧的默认参考图没有指向真正选中的首帧。** `_kfDefaultIds("last")` 往默认勾选里塞的是字面量 `"first_frame"`（`keyframe.js:50`），而素材的 id 是 `i1`、`i2` 这类编号，字面量永远不匹配，所以选中的首帧不会自动进入尾帧参考图。挑选接口每次都追加一条同角色素材（`app.py:1299`、`case.py:368`），连续挑两张首帧会在素材列表里留下两条 `first_frame`。
5. **图片轮次混在一起，工作台无法区分首帧批次与尾帧批次。** `_keyframe_rounds()` 按修改时间列出全部 `img-*` 轮次（`app.py:1212`），每条轮次只带 `stage` 与候选图；页面不知道哪一批是首帧、哪一批是尾帧。

## 2. 流程理解与一处需要说准的地方

### 2.1 分段复述

我把用户描述的流程拆成五段，每段写明输入与输出：

1. **取两帧底图。** 输入是 patch 已冻结的 `clip.mp4`，输出是 `first_frame_raw.png` 与 `last_frame_raw.png`。这一段已经由 extract 完成，不需要新入口。
2. **首帧重绘。** 输入是首帧原始图、人物三视图、首帧提示词；输出是首帧定稿图，一次出 4 张候选，人工挑 1 张。
3. **尾帧重绘。** 输入是尾帧原始图、人物三视图、首帧定稿图、尾帧提示词；输出是尾帧定稿图，同样 4 选 1。首帧定稿图作为图 3 进入参考图，是为了让两次单独生成的人物身份不漂移。
4. **视频生成。** 输入是首帧定稿图与尾帧定稿图，模式 firstLastFrame，输出是整段新视频。
5. **回贴。** 输入是第 4 段的新视频与 case 的 clip 几何契约；输出是贴回原片视口的成片，再由 `assemble` 与原片前后段拼接。

### 2.2 「中间部分全部替换」需要说准

用户说「流程里会把首帧-尾帧中间全部视频部分进行替换」。这句话的结论对，范围需要精确一分：firstLastFrame 生成的是**整段 clip**，首帧与尾帧是这段生成视频的第一帧与最后一帧，它们本身也来自生成结果，不是把原始帧剪掉后只补中间。原始 clip 整段被新成片替换，然后 merge 按 `clip.json` 的 viewport 把新成片贴回原片区域。首尾原始图的作用是给图片模型提供场景、机位与占位位置，不是最终视频的边界帧。

这个区分影响两处设计：

- 工作台必须把首帧定稿图与尾帧定稿图都写进提交集，不能只写「中间段」。
- 视频时长按 clip 的实际时长推导。walk_02 是 300 帧、30fps，也就是 10 秒；firstLastFrame 的时长参数应取 10，不是文档里 dacne 案例的 13 秒。

### 2.3 素材库、图片步输入与视频提交集

> 2026-10-26 修订：图片步输入不再是固定三张。三视图之外可以追加任意细节参考图，每张带角色与用途；图号由参考图清单生成，模板正文不再写死「图2」「图3」。以下「固定契约」的表述作为当时的设计记录保留，实际以 `docs/plan/asset-library-separation-plan.md` 为准。

用户 2026-10-22 提出的问题按原文记录：

> 我觉得有一个容易发生冲突的地方：”本次提交集“是服务于视频生成模型的asset的，但是看起来你准备复用这个区域，同时让一个三视图服务于视频和图片生成模型的提交请求，虽然事实上确实如此，但是我认为有必要拆分开来

判定：拆分成立。现在页面把 `[[assets]]` 与 `[submit] selected` 当成同一件事展示，但它们是两种不同的东西。

- **素材库**是 case 级的文件集合：三视图、首尾定稿、用户上传的其他参考图。角色是库属性；增删改排都发生在这里；库里有什么，不代表本次要提交什么。
- **图片步的输入**是固定契约，不是勾选结果：图1 是原始帧，图2 是人物三视图，图3 是首帧定稿（只在尾帧批次出现）。三张图谁是谁由步骤决定，用户不需要也不会在这里勾选。
- **视频提交集**只服务视频模型：勾选哪些候选（clip/pad/文件素材）就提交哪些，存在 `[submit] selected`。

拆分规则三条：

1. 图片步不读 `[submit] selected`，也不读素材卡片上的勾选框。素材卡片上的勾选只表示「参与本次视频提交」。
2. 视频步不自动带入图片步用过的参考图。首尾定稿图进入视频提交集，是因为交接动作显式勾选了它们，不是因为图片步生成过它们。
3. 同一个文件可以被两步同时使用，但两步各自声明输入。三视图留在素材库，图片步通过 `keyframe.toml` 的 `sheet` 指针绑定它；视频步是否使用三视图，仍由视频提交集的勾选决定。

这样「一个三视图同时服务两个模型」是两份独立的输入声明指向同一个文件，不是一份选择状态被两个模型共享。用户取消视频提交集里的三视图，不会让图片步失去它；用户在图片步换了三视图，也不会悄悄改变视频提交集。

## 3. 已拍板的五个设计项

### 3.1 工作台命名

推荐把这一步命名为「首尾帧」，面板顶部显示当前状态（`首帧待定` / `首帧已定 · 尾帧待定` / `两帧已定`）。步骤条空间有限，只放短名；「重绘」的含义放在面板首行的说明里。

- 推荐理由：名称直接说输出物是两张重绘过的帧；「工作台」是内部用语，对非技术用户没有信息量。
- 备选：「两帧定稿」强调结果，「首尾画面制作」语气更接近制作但不含「在原始帧上改」的意思。

### 3.2 两次生成都只能由按钮提交（2026-10-26 修订）

本节的初稿推荐「点选首帧后自动接尾帧」，该设计已撤销。

- 一次点击同时触发计费提交，用户没有确认的机会；首帧挑错时尾帧整批跟着作废，损失的额度比省下的那次点击大得多。
- 现在的路径：点候选只写素材与 `keyframe.toml`，页面自动切到「尾帧」步骤并提示「尾帧不会自动生成」；尾帧批次由用户点「生成尾帧候选」提交。
- 首帧批次同理，只能由「生成首帧候选」按钮发起。定稿接口不产生任何任务队列条目。
- 「不推荐首帧自动取第一张」的结论不变：定稿永远由用户点选候选完成，不做自动挑选。

### 3.3 图片步提示词框架

推荐两个模板加四个共用字段。

- 新增 `keyframe-first.md` 与 `keyframe-last.md` 两个模板，共用 `figure`（人物外观）、`pose_first`（首帧姿态）、`pose_last`（尾帧姿态）、`preserve`（必须保持）四个变量。
- 「局部编辑」「界面清理」「画质」「禁止项」写成模板固定段落，不占输入框。
- 用户只看到四张变量卡；改一次人物外观，两步同时生效；尾帧模板引用图 3 锁身份，不重复描述首帧姿势。

### 3.4 本轮范围

推荐本轮只做 patch 的图片工作台与到视频步的交接，不做工作台内的视频提交。

- 图片两步、候选挑选、两帧展示、把两帧写入提交集都在本轮；两步生成都由按钮手动提交（2026-10-26 修订，见 §3.2）。
- 「用这两帧生成视频」只做交接：切到 firstLastFrame、勾选这一对、把时长填成 clip 时长、跳到「生成」步骤并展开视频提示词。真正的提交仍由底栏的「提交生成」完成，保持扣费入口只有一处。
- gen 流程的同名入口、fullredraw（已判定与首尾帧互斥）、mid_frame 生成、不人工挑选的全自动模式都不在本轮。

### 3.5 工作台放在哪一层

用户在同一轮对话里提出的问题按原文记录：

> 我在考虑要不要把关键帧工作台做成和”生成“一个级别的步骤更好？先做设计，你已经了解了流程，我需要你从使用的简易程度和维护成本出发考虑方案

判定：独立步骤成立。推荐把首尾帧重绘做成 patch 的独立步骤，插在「抽取」与「生成」之间，步骤条变成「选区 / 抽取 / 首尾帧 / 生成 / 合并 / 对比」。标签写「首尾帧」，并在面板首行注明「用首尾帧生成视频时才需要，其它模式可以跳过」。

独立一步的理由四条：

- **扣费入口单一。** 底栏的「提交生成」只在生成步骤显示（`wizard.js:36` 的 `gen-step` 类控制）。工作台留在生成页时，用户在挑图片候选的同时也能看到视频提交按钮，两种额度的操作混在一个视口里；独立成步后，图片步只有「生成候选」按钮，视频步只有底栏，谁花钱一目了然。
- **顺序与前置关系一致。** 首尾帧的输入是抽取产物，输出是生成步的输入；放在抽取之后、生成之前，步骤条本身就表达了依赖，不需要在生成页里靠折叠区标题解释。
- **页面长度。** 工作台展开后包含两张底图、四个输入卡、两组候选网格，和素材库、提示词、最近成片叠在同一页会很长；独立面板把生成页恢复成「素材 + 提示词 + 结果」三块。
- **发现成本。** 折叠区默认收起，非技术用户容易直接看到底栏就点提交；步骤条上的「首尾帧」是一个可点击的入口，门控通过后还会打勾。

维护成本逐项列出：

- 新增 `partials/keyframe.html` 与 `pnl-keyframe`，把现有工作台的 HTML 从 `partials/generate.html` 搬过去，属于搬家不是重写。
- `wizard.js` 的 `FLOW_STEPS.patch` 增加一行；`showStep` 不需要新分支，因为底栏的显示条件已经是「当前步骤是 generate」。
- 服务端 `_gates` 增加 `keyframe` 一项：没有原始帧时给出「先完成抽取」，没有三视图时给出「素材库缺少人物三视图」，两张定稿齐全才算通过。
- 交接动作从「展开下方折叠区」变成「写模式与提交集，然后 `showStep("generate")`」。
- 代价是 patch 多一个步骤标签。不用首尾帧的用户会看到一个可选步骤，用标签上的「可选」说明抵消；这比让所有 patch 用户都在生成页里滚过一个大折叠区更轻。

四个方案在简易程度与维护成本上的取舍：

- **独立步骤（推荐）。** 简易程度最高：两种扣费各有各的按钮、顺序与前置关系由步骤条表达、不用首尾帧的人可以直接跳过。维护成本中等：新增一个 partial、一行步骤定义、一个门控与一次文件搬家，后端端点复用现有实现。
- **保持生成页折叠区。** 维护成本最低，只改文案与渲染；简易程度最低：底栏在图片步同样可见，两种提交仍在一个视口里，素材库与提交集的语义只能靠说明文字解释。
- **在生成页里再套一层子向导。** 简易程度中等，用户仍在一页里来回切换；维护成本最高：一页两套向导，步骤状态、门控与返回路径都要各维护一份。
- **做成 case 级独立页面。** 简易程度低：脱离线性流程，用户要自己记住「先做帧再回来生成」，还多一次导航；维护成本中等，收益不如独立步骤。

## 4. 目标页面与操作步骤

### 4.1 操作步骤示意

步骤条变成：`选区 / 抽取 / 首尾帧 / 生成 / 合并 / 对比`。首尾帧步骤没有底部提交条，只有本步骤的「生成候选」按钮。

```text
首尾帧（patch 的可选步骤；不用首尾帧生成视频时可以跳过）

│  [首帧原始图 1920×1080]      [尾帧原始图 1920×1080]        │

```

步骤条上的「首尾帧」在两张定稿齐全后打勾；面板顶部用一行状态说明当前进度：

```text
首尾帧    首帧已定 · 尾帧待定
```

### 4.2 两帧底图的展示

- 两张原始帧以并排大图展示，最小宽度 280px，点击在新标签页打开原图。
- 图下显示 `宽×高`、文件大小与所在 extract 版本目录名；文件缺失时整块变红并提示「先完成 extract」。
- 两张图是工作台的输入底图，不出现在素材侧边栏的提交候选里（维持决策 33 的口径）。

### 4.3 人物三视图的来源

- 三视图来自素材库，但图片步与视频提交集互不读取。图片步绑定哪一张，只由 `keyframe.toml` 的 `sheet` 指针决定。
- 首次进入时，素材库里恰好有一张 `subject_ref` 图片就自动绑定它，并写入 `sheet`；有多张时给一个下拉框，按素材顺序列出；一张都没有时显示「先到素材库添加人物三视图」并给一个跳到「生成」步骤素材区的按钮。
- 用户在图片步换三视图只改 `sheet` 指针，不改变视频提交集的勾选；反过来，用户在视频提交集里取消三视图，也不会让图片步失去绑定。
- 不自动把原始帧当三视图，也不允许在工作台绕过素材库直接添加文件；素材仍只有素材区一个入口。

### 4.4 四个字段与固定段落

- 四个字段的具体文案与模板骨架见 §5.3。
- 变量卡沿用生成页现有的提示词卡样式：显示名、键名、填写说明、多行输入框、防抖保存（`static/prompt.js`）。
- 「必须保持」预填一段通用写法：机位、构图、透视、场景建筑、背景人物、光照与色温保持图1原样；除指定人物外不新增、不删除任何物体。用户可在此基础上增补剧情相关元素。
- 「界面清理」不提供输入框，固定为「去掉画面顶部与角落的编辑器工具栏、按钮和文字，去掉后按周围画面自然补全」。若某个 case 没有界面元素，模型按「未找到则不改」处理，不需要用户判断。

### 4.5 候选与挑选

- 首帧批次与尾帧批次各自一个候选网格，只显示本步骤的候选，历史批次收进「更早的批次」折叠项。
- 一批 4 张在平台上对应 4 个并列任务，不是一个任务返回 4 张。2026-10-22 的真实首帧批次产生了任务 `2063687411157760 / 762 / 764 / 766`，每个任务一张图；旧代码只取提交应答里的第一个 `taskId`，所以只轮询并下载了 1 张。修复后 vrgen 收齐全部任务 ID、逐个轮询并下载，页面在每批候选上显示「请求 4 张 / 返回 N 张」。
- 每张候选图下面只有一个动作按钮：`设为首帧定稿` 或 `设为尾帧定稿`。当前工作台在每张图上同时给「设为首帧 / 设为尾帧」两个按钮，容易误点，本轮删除另一个。
- 挑选后候选图立即显示「当前定稿」角标，素材区同步出现对应的 `first_frame` / `last_frame` 条目。
- 挑选首帧后如果已经存在尾帧定稿，页面把它标成「基于旧首帧，需要重生成」，并从提交集里取消勾选；不删除旧文件，用户仍可查看。

### 4.6 到视频步的交接

点击「用这两帧生成视频」后：

1. 后端把 `generation.toml` 的当前模式写成 `firstLastFrame`。
2. 后端把 `[submit] selected` 写成恰好这两个素材 id。
3. 页面把底栏的时长下拉设成 clip 时长；按决策 33 的时长规则，时长不作为偏好存进 `generation.toml`，只随本次提交传递。
4. 页面切到「生成」步骤（`showStep("generate")`），展开视频提示词区，提示用户在 `gen-multi` 模板里补动作段。
5. 生成仍由底栏「提交生成」发起，避免出现第二个扣费入口。

## 5. 图片步提示词框架

### 5.1 为什么放在 vrgen 模板里

- 提示词渲染的权威已经在 vrgen：模板文件、占位符解析、显示名与填写说明都在 `vrgen/src/vrgen/prep/prompt.py` 与 `vrgen/templates/`。把骨架写在网页脚本里会造出第二份真源，违反工作区「唯一权威点」原则。
- 两个模板能被现有模板覆盖测试扫到：每个可编辑占位符都必须有显示名与填写说明，漏写时 CI 直接失败。
- 模板文件可以随 case 类型演进，不需要改前端代码。

### 5.2 变量、固定段与计算段

- 可编辑变量四个：`figure`、`pose_first`、`pose_last`、`preserve`。
- 模板固定段：局部编辑指令、界面清理、画质、禁止项。
- 计算段 `image_roles`：由本次提交的参考图顺序与角色生成，编号权威在 vrgen。例如尾帧批次渲染成「图1 = 尾帧原始图（场景、机位与占位位置底图）；图2 = 人物三视图（唯一外观依据）；图3 = 首帧定稿图（同一人物的身份锚点）」。
- 模板正文控制在 2000 字以内（专业图片-2.5 的提示词上限，`mglc model --type image --model-id 44` 查询结果）。

### 5.3 模板草案

`keyframe-first.md`：

```text
对图1做局部编辑，只改指定区域，其余像素尽量保持。
【参考图分工】{image_roles}
【替换目标】把图1中的白色占位人形替换成人物。白色人形只是占位模型，只表示位置与大小，它的站姿、手臂位置与关节角度都不继承。
【首帧姿态与位置】{pose_first|首帧姿态|写首帧里人物的姿势、朝向、与占位人形的相对位置；决定视频从哪里开始。}
【人物外观】严格按图2：{figure|人物外观|写人物的年龄、体型、发型、服装、配色与标志性饰物；从三视图抄要点。}只取图2的脸、发型、服装与配色，不取它的背景与站姿。
【必须保持】{preserve|必须保持|写机位、构图、场景与光照里不能变的部分；已预填通用写法，可按剧情增补。}
【界面清理】去掉画面顶部与角落的编辑器工具栏、按钮和文字，去掉后按周围画面自然补全。
【画质】写实质感，人物光效与场景一致，主体清晰可辨。
【禁止】不残留白色占位人形；不新增其他人物或物体；不改变机位与构图；不出现字幕、水印、Logo。
```

`keyframe-last.md`：

```text
对图1做局部编辑，只改指定区域，其余像素尽量保持。
【参考图分工】{image_roles}
【替换目标】把图1中的白色占位人形替换成人物。白色人形只是占位模型，只表示位置与大小，它的站姿、手臂位置与关节角度都不继承。
【尾帧姿态与位置】{pose_last|尾帧姿态|写尾帧里人物的姿势、朝向与落点；决定视频在哪里结束。}
【人物外观与一致性】人物必须与图2、图3是同一个人：{figure|人物外观|写人物的年龄、体型、发型、服装、配色与标志性饰物；从三视图抄要点。}图3是同一个人的首帧定稿，以图2和图3共同锁定身份，不得画成另一个人。
【必须保持】{preserve|必须保持|写机位、构图、场景与光照里不能变的部分；已预填通用写法，可按剧情增补。}
【界面清理】去掉画面顶部与角落的编辑器工具栏、按钮和文字，去掉后按周围画面自然补全。
【画质】写实质感，与图3同一光照与色调。
【禁止】不残留白色占位人形；不新增其他人物或物体；不改变机位与构图；不出现字幕、水印、Logo。
```

### 5.4 变量存储与渲染路径

- 新增 `vrgen prompt show/save --vars-file <名字>`，默认仍是 `prompt-vars.toml`。工作台用 `keyframe-vars.toml`，视频提示词继续用默认文件，两份草稿互不覆盖。
- `vrgen image submit` 增加 `--template`、`--vars-file`、`--step`、`--image-role`（与 `--image` 一一对应，可重复）。
  - 传了 `--template` 时由 vrgen 读取 `keyframe-vars.toml` 的变量、合并 `image_roles`、渲染成完整提示词；`--prompt` 与 `--template` 二选一。
  - 渲染后的完整提示词照旧写进轮次的 `prompt.txt`，台账保持可审计。
  - `--step` 只写进 `run.json` 的 `params.step`（`first` | `last`），供页面分组，不参与平台请求。
- 计算段 `image_roles` 由 vrgen 按 `--image` 与 `--image-role` 的配对生成，网页不拼这段文字。

### 5.5 视频步提示词

视频步继续用 `gen-multi` 模板，不新增视频模板。首尾帧模式下模板里的 `{asset_list}` 会列出两张定稿图，动作段由用户在生成页现有的提示词面板填写。

本轮不做「人物外观从 `figure` 自动复制到视频模板的 `target`」。两处变量的含义不完全相同（一个是静态外观，一个是视频里的最终目标），自动同步会造成两套事实，等实际使用确认重复劳动确实严重后再立项。

## 6. 手动生成与结果回收

### 6.1 定稿不提交批次（2026-10-26 修订）

初稿让挑选接口在写完首帧素材后立即 `QUEUE.submit` 尾帧批次，这个设计已撤销。

- 现在的挑选接口只做三件事：把候选图复制成素材、更新 `keyframe.toml`、清掉被替换掉的旧尾帧（连同提交集里的引用）。
- 返回里只多一个 `keyframe_hint` 文案，不再有 `keyframe_queued`。
- 尾帧批次与首帧批次一样，只能由页面上的「生成首帧候选 / 生成尾帧候选」按钮发起；扣费入口不因定稿而增加。
- 尾帧批次失败时，首帧定稿保留，尾帧步骤显示失败原因，用户可以再点一次按钮重试。

### 6.2 结果的回收与分组

- 图片轮次本来就会把全部候选下载到轮次目录，页面通过 `/img/keyframe/<case>/<round>/<index>` 读取，不需要新的下载接口。
- 新增的 `params.step` 让工作台只展示当前步骤的批次；默认展开最新一批与当前定稿所在的那一批（定稿可能来自更早的批次，只展开最新会让「已定稿」徽标消失），其余按时间倒序收进「更早的批次（N）」折叠项，首帧与尾帧两步用同一套规则。
- 每批候选图保留原始分辨率，页面用缩略图网格展示，点击打开原图。

### 6.3 当前这一对的指针

新增 case 级文件 `keyframe.toml`，记录工作台当前认定的首帧与尾帧：

```toml
extract = "20261022-164714"   # 这一对定稿基于哪个抽取版本
sheet = "i1"                  # 图片步使用的人物三视图；与视频提交集的勾选无关

[first]
round = "img-20261022-..."
index = 2
asset = "i3"

[last]
round = "img-20261022-..."
index = 1
asset = "i4"
```

`extract` 与 `case.extract_current` 不一致时，页面把这一对标成「抽取版本已更新，需要重新定稿」，并禁用交接；旧素材与旧轮次保留，不自动删除。重新抽取会改 clip 几何与两张原始帧，旧定稿不再代表当前构图。

- 写入发生在挑选接口，读取发生在页面渲染与「用这两帧生成视频」的交接。
- 不用「最新修改时间的同角色素材」推断当前这一对：素材被复制、检出或重新添加都会改修改时间，顺序不可复现（`firstlast-dev-plan.md` WP3-3b 已记录同样的理由）。
- 旧的首帧与尾帧素材不删除，只从提交集里取消勾选；用户可以在素材区查看历史。

  - 「用这两帧生成视频」调 handoff，刷新 `info`、切到「生成」步骤并展开视频提示词区。

## 8. 前置条件与风险

- **三视图必须先进入素材库。** walk_02 当前没有 `[[assets]]`，需要把 `sources/大臣_三视图.png` 以 `subject_ref` 加入一次，图片步才能绑定 `sheet`。这是每个 case 只做一次的前置，不是每次生成都要做。
- **可选步骤会给所有 patch case 多一个标签。** 只用 videoEdit 的用户会看到未完成的「首尾帧」步骤。软向导不阻止跳过，标签注「可选」并写一句「用首尾帧生成视频时才需要」；如果实际使用中这个标签造成明显干扰，再考虑按模式隐藏，但那会把模式选择提前到步骤条之前，成本更高。
- **`sheet` 指针可能指向被删除的素材。** 删除素材时同步清空 `sheet`（`remove_asset` 的既有逻辑扩一条），下次进入首尾帧步骤重新绑定；不在删除时自动改指另一张三视图，避免静默换人。
- **项目会话修复是硬前置。** 不传 `--session-id` 时图片任务落个人额度（决策 22 已记录个人额度为 0）。WP2 必须与页面改造一起提交，不能只改前端。
- **首次真实图片提交仍有未验证点。** 图片任务返回的 URL 形状（R2）、参考图体积上限（R9，单张 30MB）、4K 出图的额度消耗都只在真实提交后才能确认；walk_02 的两张原始帧是 1.3–1.5MB，不触发体积上限，但 4K 候选图的体积未知。
- **4K 默认值的成本。** 两批各 4 张 4K 图，成本明显高于 2K。计划保留模型最高档为默认（与 `firstlast-dev-plan.md` WP0.5 一致），但在生成按钮旁显示「本次 4 张 · 4K」，并允许单次下调到 2K。
- **firstLastFrame 的成片宽高未实测（R7）。** 16:9 + 1080p 的真实返回尺寸要等首次提交后记录；merge 已按比例校验，不会静默拉伸。
- **尾帧与首帧的配套关系靠指针维持。** 如果用户绕过工作台，在素材区手动更换 `first_frame`，`keyframe.toml` 不会自动更新。交接时以 `keyframe.toml` 为准，并在页面提示「当前两帧由工作台记录」；手动改素材属于高级路径，不在本轮校验。
- **模板渲染与素材顺序耦合。** `image_roles` 的文字必须与实际传入顺序一致；WP2 固定顺序、WP1 按顺序生成文字，两侧测试各钉一条，避免编号漂移。

实测发现（2026-10-22）：

- **一批 4 张对应 4 个并列任务，旧代码只取了一个。** 首帧批次用 `--num 4` 提交后，平台产生了 `2063687411157760 / 762 / 764 / 766` 四个任务，每个任务一张图。`extract_task_id` 只取提交应答里的第一个 `taskId`，所以 vrgen 只轮询并下载了 `760` 的那一张（run `img-1ce2b5e4`），页面显示一张不是漏渲染。修复：新增 `extract_task_ids` 收齐全部任务 ID，`Run.task_ids` 记录它们，`execute_image_round` 逐个等待，`_fetch_all` 逐个取 URL 并去重下载；`run.json` 增加可选 `task_ids` 字段。已经用只读的 `mglc task status` 把 `762/764/766` 三张图补回同一个轮次，`results` 现在是四张 3840×2160 候选。页面在每批候选上显示「请求 4 张 / 返回 N 张」。
- **首帧定稿质量。** 补回的四张候选均为同一场景下的坐姿高官，白色人形消失、顶部工具栏与右下角文字被去掉、场景与光照保持；四张之间的细微差异留待用户挑选。
- **firstLastFrame 的输出分辨率下拉被误禁用。** `params.js` 把“输入档位为空”当成“还没有素材”，把输出分辨率与输入缩放两个下拉框一起禁用。firstLastFrame 没有输入视频，`input` 必然为空，于是输出分辨率也被锁住，用户只能看到第一项 480p 且无法改。修复：输出与输入分开判断，只有 `output` 为空才禁用输出下拉；`current.resolution` 正常回显。walk_02 的 `generation.toml` 曾被写成 480p，已改回 1080p。

### 2026-10-23 补充：时长自动推导与预演回弹

- patch 的 `firstLastFrame` 时长改为从当前 `clip.json` 的帧范围与帧率推导整秒：`clip_duration_s()` 在 vrstudio 里计算（294 帧 @30fps → 10 秒，最小 4），`generate submit` 在未显式给 `--duration` 时把它传给 vrgen。gen 没有 clip，仍回退到纯图片默认 4。
- 页面由 `_generation_params` 下发 `auto_duration_s`，时长下拉的“自动”显示成“自动（约 N 秒）”，`fixed.duration_s` 同步回显这个推导值；它只是提示，不是持久化草稿。
- 预演回弹的原因：`params.js` 的 `_fillDuration()` 每次重画都执行 `sel.value = "auto"`。预演返回后 `renderAll()` 重画下拉，手动选的 10 秒被刷回自动，预演签名比对就报“参数有改动”。现在重画时保留当前选择，只有选项里没有该值才退回自动；`genDuration` 的 onchange 同时刷新生成设置的提示文字。
- 浏览器验收：walk_4k 选 10 秒 → 预演检查 → 下拉仍为 10，状态显示“✓ 预演通过 · 当前选择未改动”。
- 测试：新增 `clip_duration_s`、submit 默认/显式时长、`_generation_params` 的 `auto_duration_s` 用例。

### 2026-10-23 补充：pick 点击后下方预览像没更新

- 现象：在 walk_4k 的选区页点顶部全景视频，viewport 已经变化，但下方 1920×1080 预览要等很久才动，连续点击时像完全没有反应。
- 原因：`api_viewport` / `api_nudge` / `api_inner` 每次都返回完整的 `_case_info`。4K case 上这份信息要重扫 4K 素材与两张 4K 原始帧，单次 4–7 秒；前端 `post()` 要等完整响应才更新预览 URL，点击因此排队。
- 修复：三个几何端点改为返回轻量 payload（`viewport` / `inner` / `previews.vp`），前端用 `fetchGeometry()` 取回后 `applyGeometry()` 合并并只重画选区，不再重扫素材。`reset-draft` 同样改走轻量应答。
- 浏览器验收：walk_4k 点击后约 185 ms 预览 URL 更新，新图加载约 206 ms；点击到画面更新约 0.4 秒，点击不再排队。
