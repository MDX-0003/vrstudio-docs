# Patch 时间拼接开发计划（方向已定，待实施）

本文讨论“中间段完成空间合并后，把原片前后段拼回同一条时间轴”的开发计划，不改变已经冻结的 `clip.json` 字段集。空间合并与时间合并拆成两个独立 CLI 入口，前端串联；`frames` 精确等于 AIGC 重绘范围，不做前后余量；编码统一 H.264 8-bit yuv420p。输出命名、CLI 命令名和对比页默认值还需要确认，标在文末。

## 目标

当 patch case 的 `[frames]` 不是整条源片时，前端串联空间合并与时间合并，输出一条与源片等长的视频：

- 前段：源片 `[0, frame_start-1]`，不经过 AIGC。
- 中段：空间合并产出的段，对应源片 `[frame_start, frame_end]`。
- 后段：源片 `[frame_end+1, 源片最后一帧]`，不经过 AIGC。

`frames` 精确表示要重绘的内容：切出 x 帧，完整重绘 x 帧，再在时间和空间上恢复；不做前后余量，不增加独立的替换范围。

输出保持源片 fps、源片帧数、源片音频；视频编码按决策 19 的 H.264 8-bit yuv420p delivery 档。

## 当前状态

- `extract` 按 `[frames] start/end` 冻结 `clip.json`、`clip.mp4`、`clip_mask.png`。
- `merge` 从源片 `seg.frame_start` 开始，空间合并 `n_seg = end - start + 1` 帧，写到 `out/<抽取版本>.mp4`；当前输出只有这一段，不包含前缀和后缀。
- `merge` 已经做出正确的位置合并：viewport/inner 来自 `clip.json`，只替换 inner，viewport footprint 之外在段内不变。
- 空间合并输出的帧数和 fps 已经是 `n_seg` @ 抽取 fps：AI 返回件在空间合并前由 `restore` 转成这个目标（24fps 的 AIGC 结果也在这一步转回 60fps），`FfmpegSink` 按 `sidecar_fps` 写满 `n_seg` 帧。
- 当前对比页把整条源片和段成片都从时间 0 开始同步，没有 `frame_start / fps` 偏移；抽取整条源片时看不出问题，抽中间段时时间轴会对不上。

## 设想行为

1. 检测非整片抽取：用 `clip.json` 里冻结的 `frame_start/frame_end` 和源片实际帧数比较；整片抽取不触发时间拼接，保持现有空间合并输出。检测不用 case.toml 草稿，避免改了草稿但未重新抽取时误判。
2. 空间合并保持独立 CLI：沿用当前 merge 的投影、inner 融合和 AI 时间对齐，输出 `out/<版本>_space.mp4`。
3. 时间合并是独立 CLI `vrstudio assemble`：输入源片、`_space.mp4` 和 `clip.json`，把源片前缀、空间合并段、源片后缀按顺序写成 `out/<版本>_frame.mp4`；中段第 0 帧对应源片 `frame_start`，输出第 i 帧对应源片第 i 帧。
4. 前端把空间合并和时间合并作为两个连续队列任务：`merge` 成功后自动提交 `assemble`，把 `_space.mp4` 路径作为输入参数；两步独立日志、独立重试，空间合并失败时不会进入时间合并。
5. 输出保持源片帧数和 fps，音频从源片复用；视频统一 H.264 8-bit yuv420p。
6. 对比页优先读 `_frame.mp4`，读不到再读 `_space.mp4`；非整片且只有 `_space.mp4` 时标注“仅中间段”。

## 实现路线

### 路线 A：两个独立 CLI（已选）

1. 现有空间合并 CLI 保持独立，产出中间段 `out/<版本>_space.mp4`。
2. 新增独立的时间合并 CLI `vrstudio assemble`，输入源片、中间段、`clip.json`，输出完整成片 `out/<版本>_frame.mp4`。
3. web 的 merge op 在空间合并成功后，把空间合并的输出路径作为参数提交时间合并；两步独立可跑，串联后自动完成。
4. 优点：现有空间合并和像素基线不动，时间合并可以单独测试；失败时能保留中间段。
5. 代价：中间段会被再解码一次，视频编码多一代；完整成片的总耗时比单次流式编码高。

### 路线 B：单次流式（后续优化，不阻塞首期）

1. 在 merge 的空间合并循环外增加前缀读取和写帧，循环内写中间段，循环后读后缀并写帧。
2. 一次编码直接产出完整成片，避免中间段二次编码。
3. 需要把输出路径、进度、snapshot 帧号和报告字段一起改；现有空间合并测试需要同时覆盖整片和中间段。
4. 适合在两阶段方案稳定后做，不作为首期前置条件。

## 帧数和帧率契约

结论：空间合并的输出已经保证“帧数等于抽取段、帧率等于抽取 fps”，时间合并只需要校验并直接拼接，不需要再做一次帧率转换。

- 空间合并的目标帧数是 `n_seg = frame_end - frame_start + 1`，目标 fps 是 `clip.json` 的 `fps`（extract 时从源片读出的 fps）。
- AI 返回件在空间合并前经过 `restore`：24fps 的 AIGC 结果会被拉伸/选择/重新打时间戳到 `n_seg` 帧 @ 抽取 fps；然后 `FfmpegSink` 按这个 fps 写满 `n_seg` 帧。因此空间合并输出的段不是 24fps，而是和抽取段一致的 fps。
- 时间合并读取空间合并段后先做契约检查：`段帧数 == n_seg`、`段 fps ≈ clip.json fps`、`源片 sha256` 与 case 一致、`源片 fps ≈ clip.json fps`。检查通过后，前缀、段、后缀按同一 fps 顺序写入完整成片，不再对段做帧率转换。
- 如果检查不通过，时间合并直接报错并给出日志路径；不回退到静默重采样。帧数/fps 不一致说明空间合并或抽取契约已经坏了，应该先修上游。
- AI 返回件比目标短且 RIFE 不可用时，空间合并会重复最后一帧补足 `n_seg`；帧数契约仍然成立，但内容可能有冻结尾巴，这是内容质量问题，不是时间拼接问题。
- 源片是 VFR，或源片 fps 与 `clip.json` 的 fps 不一致时，简单按帧拼接会漂移；首期直接报错，不静默处理。当前项目源片是 CFR，正常路径不会触发。

## 编码与像素边界

- 源片可能是 HEVC 8K，中间段是 H.264 8-bit yuv420p；一个 MP4 视频流里不能同时 `-c copy` 两种编码。完整成片必须统一编码。
- 按决策 19，完整成片统一输出 H.264 8-bit yuv420p；前缀和后缀会被重新编码一次，解码后的像素内容不变，但编码字节不是原片字节。需要逐位字节一致时，只能保留原片分段或使用 EDL/播放列表，不能做成单一 H.264 MP4。
- 像素基线测试用 crf 0：前缀/后缀解码后的像素应与源片对应帧一致；中段应与空间合并段一致；整片帧数、fps、音频时长一致。
- 音频从源片复用；如果源片没有音频，输出保持无音频。

## 输出命名与下游回退

已定：

- 空间合并入口是 `vrstudio merge`，输出 `out/<版本>_space.mp4`。
- 时间合并入口是 `vrstudio assemble`，输出 `out/<版本>_frame.mp4`。
- `clip.json` 的时间区间等于整片时，不调用 `assemble`，只保留 `_space.mp4`；这时 `_space.mp4` 本身就是整片长度。
- 下游（对比页、输出选择）优先读 `out/<版本>_frame.mp4`；读不到再读 `out/<版本>_space.mp4`。整片抽取只有 `_space.mp4`，回退结果就是整片。
- 非整片抽取如果只有 `_space.mp4` 没有 `_frame.mp4`，说明时间合并还没成功；页面可以展示 `_space.mp4` 供检查，但必须标注“仅中间段”，不能把它的时间轴当成整片。
- 当前代码还写 `out/<版本>.mp4`；实施时改成 `_space.mp4`。历史 `<版本>.mp4` 不进入新回退链，由一次性迁移脚本 `scripts/migrate_out_names.py` 改名为 `_space.mp4`；脚本默认 dry-run，`--apply` 才执行，只处理 patch case 且文件名能对上已记录抽取版本的文件，fullredraw 不动，目标已存在时跳过不覆盖。
- 迁移脚本已经对现有 case 执行过一次：`web_demo` 的旧 `20261016-171617.mp4` 已改名为 `20261016-171617_space.mp4`；`ship_01` 是 fullredraw，未改。

- WP0 决策：输出命名、`vrstudio assemble` 入口、整片跳过时间合并、下游 `_frame` → `_space` 回退、两个连续队列任务、历史文件迁移脚本都已确定。
- WP1 CLI：空间合并输出改名为 `_space.mp4`；新增 `vrstudio assemble`，输入源片、`_space.mp4`、`clip.json`，先做帧数/fps/sha256 契约检查，再按源片前缀、段、后缀写出 `_frame.mp4` 和报告；整片区间直接跳过时间合并；不做帧率转换。
- WP2 web：merge op 在空间合并成功后，自动提交 `assemble` 任务，并传入 `_space.mp4` 路径；两个连续队列任务，各自日志、各自重试；合并页显示两个输出；对比页按 `_frame` → `_space` 回退，非整片只有 `_space` 时标注“仅中间段”。
- WP3 测试：整片抽取不调用 assemble；非整片生成 `_space` 和 `_frame`；前缀/后缀像素一致；中段与 `_space` 一致；帧数/fps/音频；`frame_start=0` 或 `frame_end=末帧` 的单边情况；段帧数/fps 不匹配时失败；AI 返回件短/长/比例不一致时的错误路径；下游回退顺序。
- WP4 文档：更新 `docs/patch-videoedit-example.md`、`docs/case-model.md` 的 merge 输出说明和用户教程。

## 验收标准

- 整片抽取：只生成 `out/<版本>_space.mp4`，不调用 assemble，不生成 `_frame.mp4`。
- 中间段抽取：生成 `_space.mp4` 和 `_frame.mp4`；完整成片帧数等于源片，前段/后段解码像素与源片一致，中段与 `_space.mp4` 一致，音频与源片一致。
- 下游：`_frame.mp4` 存在时优先使用；不存在时使用 `_space.mp4`；非整片且只有 `_space.mp4` 时标注“仅中间段”，不假装是整片时间轴。
- 失败路径：源片 sha 不匹配、`clip.json` 缺失、中间段帧数/fps 不匹配、AI 返回件无法 restore 时，任务失败并给出具体日志路径，不静默输出半成品。
- 编码门禁：pytest 全绿，crf 0 基线通过，ruff 干净。

## 已定事项

- 空间合并和时间合并是两个连续队列任务；`merge` 成功后自动提交 `assemble`，失败时停在空间合并。
- 历史 `out/<版本>.mp4` 由 `scripts/migrate_out_names.py` 改名为 `_space.mp4`；目标冲突跳过，不覆盖。
- 当前没有待确认的产品决策；剩余是 CLI 参数、队列任务命名、对比页标注等实现细节。

## 风险

- 8K 完整成片重编码耗时和磁盘占用明显高于中间段；长素材需要队列和进度提示。
- 前缀/后缀经过一次有损编码，和源片不是字节级一致；对画质敏感的交付需要单独评估编码档位。
- 两个独立 CLI 串联会多编码一代中间段；单次流式方案改动面更大，留作后续优化。
- `frames` 已定为精确重绘范围，不做时间余量；如果以后模型需要动作前后文才能稳定，再单独立项，不混进首期拼接。
