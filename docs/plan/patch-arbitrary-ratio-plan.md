## 2. 需求简报

### 2.1 角色与场景

- 使用者是本机的美术与开发人员。他们在 Windows 工作站上用浏览器打开源码版 vrstudio，在一个 case 内完成选区、抽取、送外部工具生成、把成片合并回全景片。
- 一条 case 的素材是 2:1 的 ERP 全景视频，多数在 4K 到 8K 之间。选区与抽取在浏览器里做，生成在芒果灵创或外部工具里做。
- 使用者对“比例”的预期来自外部工具或交付要求（例如 2.39:1 的电影画幅），而不是本系统预设的几档。

### 2.2 主任务与失败路径

- 当我要让 AI 重绘全景里的一块画面时，我想按我指定的任意宽高比切出一段视口视频，并让它的像素数刚好用满平台允许的上限，以便送进外部工具时既不变形也不浪费分辨率。
- 当我拿到一段生成或外部改好的视口视频时，我想让合并页按这段视频的宽高比自动列出所有同比例的抽取记录，我在其中挑一条范围和时点合适的来合并，以便不用回头重切。
- 当这段视频的比例与所有记录都不一致时，我要能选最接近的一条强制执行合并，并在报告里看到比例差与裁切结果，而不是被卡住无法出片。
- 当抽取区间不是整片时，合并完成后系统仍按现有规则自动排队时间拼接，我不用额外操作。
- 当视口比例不在当前图片模型的比例表内时，首尾帧入口要明确告诉我原因并给出可行路径（改用 videoEdit 或换比例），而不是生成到一半才失败。

### 2.3 约束

- 冻结契约不扩字段：`clip.json`、`_pad.json`、`run.json` 的字段集保持不变。比例与分辨率继续由 `clip.json` 的 `viewport.width/height` 承载。
- 只改视频 patch。patchimg 的 `image.json` 仍要求 16:9，fullRedrawImg 仍固定 21:9，gen 流仍固定 16:9。
- 像素预算的上下限默认取 409600 与 2086876，优先读平台，读不到用内置默认；配置可覆盖。
- 配置在进程启动时载入，运行中改文件不生效，重启生效。这符合“启动前可以随意调整”的要求，本轮不开运行期配置入口。
- 合并接受宽高比差距 1%。生成侧如果 CLI 只支持固定比例，就按 CLI 的限制调整，切分侧不跟着收窄。
- 提交门禁仍是 `uv run pytest` 全绿、`uv run ruff check .` 干净，前端 `npm run lint`、`format:check`、`test`、`build` 通过。

### 2.4 验收

- 在选区页选预设 `2.39:1`，页面显示派生尺寸 `2216×928`（2,056,448 像素）、只读预算与“该视口在源片里覆盖约 N 像素”的参考读数。
- 选预设 `16:9`，派生尺寸是 `1920×1080`，与现有行为一致。
- 切到“自由框选”，在全景图上拖一个 16:9 的矩形，右侧显示“框 1.78:1 · 投影后约 1.99:1”，派生尺寸按 1.99:1 算；框住的范围与预览覆盖一致。
- 预算只读：页面上没有预算输入或下拉，读数写明来自 `vrstudio.toml`；改配置后重启才生效。
- 抽取完成后 `clip.json` 的 `viewport.width/height` 等于页面显示的派生尺寸，`clip.mp4` 的宽高与它一致。
- 合并页在选定一段 2216×928 的成片后，只列出宽高比差距在 1% 以内的抽取记录，每条显示版本、取景摘要、时间范围、像素数与“成片宽高比 X 与这条记录 Y 的差距 Z%”。
- 从某版本生成的成片，该版本排在第一位并默认选中，其它同比例记录带“取景或时间不同，切换可能导致画面错位”的提示。
- 没有任何记录落在 1% 以内时，页面列出最接近的 1–3 条并显示比例差，点“强制合并”能出片，`report.json` 记录比例差与裁切方式。
- 16:9 的既有 case 重跑 extract 与 merge，产物与改动前逐字节一致（pixel baseline 门禁）。
- 视口比例为 2.39:1 时，首尾帧入口显示“当前视口比例 2.39:1 不在图片模型支持的比例表内”，videoEdit 路径不受影响。

### 2.5 范围三栏

- 现在必须做：任意比例切分（预设下拉 + 自由框选）、预算派生尺寸、配置键、合并按比例匹配、候选列表与提示、强制合并出口、首尾帧比例派生与失败说明、16:9 回归。
- 以后可以做：把比例标签写进抽取目录的独立报告文件（不改 `clip.json`）、运行期配置入口、按模型分别配置预算、patchimg 放开比例。
- 明确不做：改 `clip.json` 契约、patchimg 与 fullRedrawImg 的比例、gen 流的 16:9、自动裁切且不询问用户、在选区页把非标比例偷偷吸附到标准比例。

### 2.6 优先级

先做“任意比例切分 + 按比例匹配合并”这一条闭环，因为它是需求的主干；首尾帧的比例派生排第二，它决定非标比例下哪些生成模式可用；页面美化与历史记录迁移排最后。

### 3.5 范围与宽高比差距的落点

- 可变层：`case.toml` 的 `[[range_preset]]` 是保存的选区，每条带 `id`、`created_at/updated_at`、`[range_preset.viewport]`（含 `width/height`）、`[range_preset.inner]`、`[range_preset.frames]`；`[pick] active` 指向当前条。旧格式的顶层 `[viewport]/[inner]/[frames]` 在加载时合成 `r1`，保存时迁移成新格式。
- Web 草稿：`derived/pick/draft.toml` 是 pick 页的工作草稿，带 `source_sha256`、`updated_at`、`viewport/inner/frames`。它不是契约，CLI 不读；点全景、拖 inner、改 fov、换比例只写它。
- 冻结层：`extracts/<version>/clip.json` 是抽取版本的几何权威（`version=1`、单段、`erp_width/height`、`fps`、`segments[0].frame_start/end`、`viewport` 含 `width/height`、`inner`）；同目录还有 `clip.mp4`、`clip_mask.png`、`first_frame_raw.png`、`last_frame_raw.png`。`[extract] current` 指向最新版本；`derived/clip.json` 是最新版的副本，供 `--sidecar derived/clip.json` 兼容用法。
- 版本目录不可变：改 preset 或 draft 后重新 extract 会生成新版本，旧版本不动。`clip.json` 不记录 preset id，也不记录这次是预设比例还是自由框选切的；比例一律从 `viewport.width/height` 推出。
- AI 结果：`extracts/<version>/result.mp4`（adopt 落点）或 `[merge] input` 指向的素材；合并前用 ffprobe 读它的宽高。
- 合并页只列抽取版本，不列未抽取的 preset；preset 只在几何匹配时作为标签出现（`docs/case-model.md` §2）。
- 宽高比差距：`|ai_ratio / record_ratio - 1| ≤ aspect_ratio_diff_pct / 100`，其中 `ai_ratio = ai_w / ai_h`、`record_ratio = vp_w / vp_h`。它只比比例，不比分辨率、帧数或画面内容。默认 1.0。
- 0.1% 是现有 `normalize_ai_frame` 的等比阈值；0.1%–1% 走覆盖缩放加居中裁切；超过 1% 拒绝，除非显式 `--allow-crop`。

## 4. 方案

### 4.1 两种比例来源与只读预算

- 选区提供两种比例来源：预设比例下拉（16:9、9:16、1:1、4:3、3:4、3:2、2:3、21:9、2.39:1、1.85:1）与自由框选（在全景图上拖一个矩形）。
- 预设模式按比例优先：比例来自下拉，yaw 与 pitch 由点击全景图决定，fov 由滑杆决定；改 fov 时左侧 footprint 与右侧预览一起变，比例保持不变。
- 自由模式按范围优先：框的中心定 yaw 与 pitch，框的宽度定 hfov，框的高度定 vfov，视口比例由 `tan(hfov / 2) / tan(vfov / 2)` 算出；左侧框住的范围与右侧预览覆盖的范围一致，但输出比例可能不等于框的像素比。自由模式没有单独的 fov 滑杆，框就是取景控制。
- 框的宽或高小于全景图的 2% 时忽略，避免拖出零尺寸。
- 视口像素由“比例 + 像素预算”派生，页面只显示结果，不允许直接改宽高。预算只从配置读，页面最多显示数值，不提供调节控件。
- 记录的比例以 `clip.json` 的 `width/height` 为准。派生尺寸 `2216×928` 的实际比例是 2.38793，后续匹配、显示、报告都用实际值。

### 4.2 派生尺寸算法

输入是精确比例 `r`、像素上限 `P`、像素下限 `M`、对齐步长 `A`。输出是满足 `M ≤ W×H ≤ P`、`W` 与 `H` 都是 `A` 的倍数、比例最接近 `r` 的一组尺寸。预设比例给出 `r` 的精确有理数；自由框选给出框的像素宽高比 `(dx × erp_width) / (dy × erp_height)`，可以是任意正数。

1. 连续解：`h0 = sqrt(P / r)`，`w0 = h0 * r`。
2. 在 `h0` 附近上下各 4 个对齐步长内枚举 `h`（`h` 是 `A` 的倍数），每个 `h` 取 `w = round(A * round(h * r / A))`。
3. 丢掉面积超出 `[M, P]` 的候选。
4. 丢掉比例误差超过一个对齐步长（`A / min(W, H)`）的候选，因为再精细也受整数尺寸限制。
5. 在剩下的候选里取面积最大的一组；面积相同取比例误差最小的一组。
6. 没有候选时，先按比例误差最小选一组；仍然没有就报错，报错文案给出该比例下能满足下限的最小面积与当前预算。

对齐步长取 8，不取 16。`1920×1080` 的高度 1080 不是 16 的倍数，按 16 对齐会得到 1904×1072 或 1936×1088，都不是 1080p；8 是 yuv420p 与 1080p、1440p 都能命中的最小对齐。

在默认预算下的四个例子：

- `16:9` → `1920×1080`，2,073,600 像素。
- `1:1` → `1440×1440`，2,073,600 像素。
- `9:16` → `1080×1920`，2,073,600 像素。
- `2.39:1` → `2216×928`，2,056,448 像素，实际比例 2.38793。

### 4.3 配置

新增 `[patch]` 段，键与默认值如下。

- `viewport_max_pixels = 0`：0 表示优先读平台 `maxPixel`；平台读不到时用内置默认 2086876；填正整数时以配置为准，用于临时压低预算。
- `viewport_min_pixels = 0`：0 表示优先读平台 `minPixel`；读不到用内置默认 409600；填正整数时以配置为准。
- `aspect_ratio_diff_pct = 1.0`：候选筛选与合并接受共用的宽高比差距上限，单位是百分比。
- `viewport_align = 8`：派生尺寸的对齐步长。留成配置是为了以后平台要求 16 或 32 对齐时不用改代码，默认不要动。

优先级从高到低是：显式配置（非 0）→ 平台模型详情 → 内置默认。内置默认写在 `vrstudio/config/default.toml` 与 `vrstudio/src/vrstudio/config.py` 的 `_FALLBACK` 两处，`tests/test_config.py` 的同步断言覆盖它们。前端只读显示生效值；两个选区端点都不接受预算参数，避免页面绕过项目配置。

### 4.4 抽取产物不变

- `clip.json` 不新增字段，`version` 保持 1。比例与分辨率继续从 `viewport.width/height` 推出。
- `clip.mp4`、`clip_mask.png`、`first_frame_raw.png`、`last_frame_raw.png` 的生成逻辑不变，只是尺寸可能不再是 16:9。
- extract 的日志增加一行“比例 2.38793（预设 2.39:1 / 框选 18.9%×15.8%），预算来源 platform，2,056,448 / 2,086,876 像素”。
- `case.toml` 的 `[viewport]` 仍写宽高，不新增 `ratio` 键；派生的比例标签每次从宽高算，避免两个来源打架。

### 4.5 合并按比例匹配

- 新增 `GET /api/case/{name}/merge-targets`。它解析当前合并输入：有 `[merge] input` 时用那条素材的文件，否则用查询参数 `?extract=<版本>` 指定版本的 `result.mp4`，缺省用 `[extract] current`；用 ffprobe 读宽高，算出实际比例与标签。
- 服务端把 `_merge_ranges` 的分组按 `|成片比例 / 记录比例 - 1| ≤ aspect_ratio_diff_pct / 100` 分成两组：
  - `exact`：所有宽高比差距在 1% 内的分组，按“帧范围覆盖成片时长优先、抽取时间最新其次”排序。
  - `near`：没有 `exact` 时，取差值最小的 1–3 个分组，带 `diff_pct`。
- 每个分组带 `viewport`、`inner`、`frames`、`pixels`、`ratio`、`ratio_label`、`aspect_ratio_diff_pct`、`origin`。`aspect_ratio_diff_pct` 是“成片宽高比”与“这条记录宽高比”的相对差距；`origin` 为 true 表示这段成片就是这个版本生成的（`result.mp4` 位于该版本目录）。
- 默认选中规则：`origin` 分组优先；没有 `origin` 时取 `exact` 的第一组；`exact` 为空时默认不选，等用户点“强制合并”。
- 切换非 `origin` 的 `exact` 分组时，页面显示一次提示：“这段成片按另一组取景生成，切换范围或时点可能导致画面错位；功能不限制，出片后请核对。”提示只在切换时出现，不阻塞操作。
- `near` 分组的行显示“比例差 X%，强制合并会按覆盖缩放并居中裁掉边缘”。点“强制合并”发 `{op: "merge", extract: <版本>, allow_crop: true}`，沿用现有 `--allow-crop` 通路。
- 搜索范围只有抽取记录，不新增“手工指定宽高”的入口：合并目标必须来自 `clip.json`，否则贴回几何没有权威来源。

### 4.6 宽高比差距只有一个数

- 现在有三个不同的阈值：`AiFrameSource` 的 0.1%、`--allow-crop` 的任意差、fullRedrawImg 的 2%。本轮把视频 patch 的两个合并成一个 `aspect_ratio_diff_pct`（默认 1.0），列表筛选与合并接受都用它。
- 合并内部的处理规则改成一条：
  - 比例差 ≤ 0.1%：直接等比缩放到视口尺寸，不做裁切，报告记 `normalize_mode = "uniform"`。
  - 0.1% < 比例差 ≤ 宽高比差距上限：覆盖缩放加居中裁切，报告记 `normalize_mode = "cover_crop"`、`aspect_diff_pct` 与实际裁掉的像素数。
  - 比例差 > 宽高比差距上限：报错，除非显式 `--allow-crop`；显式放行时同样走覆盖缩放加居中裁切，报告记 `normalize_mode = "cover_crop_forced"`。
- 覆盖缩放的语义沿用 `patch/composite.py` 的 `normalize_ai_frame`，不写第二套缩放规则。

### 4.7 首尾帧与非标比例

- `_keyframe_ratio` 从 `case.viewport.width/height` 推出比例标签。标签必须在当前图片模型 `ratios` 里，命中才返回；没命中时返回空并给出原因。
- `_keyframe_ratio_or_none` 保持“几何不合约不把整页打成错误”的现有行为，返回 `None`。
- `_mode_ready` 的 firstLastFrame 分支把“视口是 16:9”改成“视口比例在当前图片模型的比例表内”。模型能力读不到时用平台公开的八个比例兜底。
- `api_keyframe_run`、`api_keyframe_pick`、`cli/generate.py` 的 `_require_16_9` 都改成按 `clip.json` 的实际比例校验，错误文案统一为“视口实际比例 X 与首尾帧 Y 不一致；首尾帧必须与视口同比例”。
- 非标比例（例如 2.39:1）下，首尾帧入口置灰并说明：“当前视口比例 2.39:1 不在图片模型支持的比例表内；要么改比例，要么用 videoEdit。”videoEdit 的输入就是 clip 本身，不受影响。

### 4.8 页面交互

可点击原型：`vrstudio/.tmp_prototype/arbitrary-ratio.html`（不进 git，只用于评审）。打开后可以在“现状 / 提案”之间切换，也可以用 `?page=merge&state=next&input=upload185` 直接看无同比例记录的形态。

选区页：

### 4.9 自由框选的两种语义

- 框在 2:1 ERP 上有两个读数：像素宽高比 `w / h` 与角度宽高比 `hfov / vfov`。因为 360°/3840 px 与 180°/1920 px 都等于 0.09375°/px，这两个读数相等。
- rectilinear 输出不是线性映射，它的像素宽高比是 `W / H = tan(hfov / 2) / tan(vfov / 2)`。所以输出的像素比不等于角度比，除非角度很小。
- 语义 A（预设模式）：`hfov` 取滑杆角度，`W / H` 取预设比例，`vfov` 由 `vfov = 2 × atan(tan(hfov / 2) / 比例)` 反推。输出比例精确等于预设，左侧 footprint 的角宽高与右侧预览的像素比不同。
- 语义 B（自由模式）：`hfov` 取框宽角度，`vfov` 取框高角度，`W / H` 由 `tan(hfov / 2) / tan(vfov / 2)` 算出。框住的范围与预览覆盖一致，但输出比例不等于框的像素比。
- 例子（ERP 3840×1920，0.09375°/px）：
  - 16:9、30°：框 320×180 px。A 的 `vfov` 是 17.14°（框高 16.88°，多 1.6%），B 的比例是 1.806（比 16:9 偏 1.6%）。两者几乎一样。
  - 16:9、75°：框 800×450 px。A 的 `vfov` 是 46.69°（框高 42.19°，多 10.7%），B 的比例是 1.989（偏 11.9%）。
  - 2.39:1、68°：框 725×303 px。A 的 `vfov` 是 31.50°（框高 28.44°，多 10.8%），B 的比例是 2.660（偏 11.3%）。
  - 4:3、60°：框 640×480 px。A 的 `vfov` 是 46.83°（框高 45.00°，多 4.1%），B 的比例是 1.394（偏 4.5%）。
  - 4:3、120°：框 1280×960 px。A 的 `vfov` 是 104.82°（框高 90.00°，多 16.5%），B 的比例是 1.732（偏 29.9%）。视场角越大，两种语义差得越远。
- 为什么二选一：输出只有 `hfov` 与 `vfov` 两个自由度，比例由它们决定。框给出 `hfov` 与 `vfov` 两个约束；再要求比例等于 `w / h` 就是三个约束，一般无解。语义 A 放弃“`vfov` 等于框高”，语义 B 放弃“比例等于框的像素比”。
- 左侧是等距柱状投影，右侧是透视投影。B 让两者的覆盖范围（角度边界）一致，但边框的像素形状仍然不同：ERP 上的 16:9 框投到透视图上会变成 1.99:1。要求边框形状也一致，只能回到 A，让预览多收竖向画面。这两个“一致”不能同时成立。
- 两个模式各用一条：预设模式用 A（比例优先），自由模式用 B（范围优先）。自由框选的“框住哪里就覆盖哪里”成立，预设模式保留标准比例。代价是自由模式的输出比例是 tan 结果（例如 16:9 框在 75° 下是 1.99:1），要标准比例就切回预设模式。

## 5. 排除的方案与理由

- 只放开模型支持的八种比例：不满足“字面意义上的任意”，2.39:1、1.85:1 这类交付画幅拿不到。
- 手填宽高比与像素预算：初版原型证明交互成本太高；预算应该由项目配置统一，比例用预设下拉与自由框选覆盖。
- 自由框选只取比例、不取中心与视场角：用户希望一次框选同时决定“框在哪、框多宽、什么比例”，少一步操作。
- 任意比例且首尾帧也支持：非标比例要先把画布补边到最近的支持比例，生成后再裁回；补边区域可能被模型重绘，贴回边界会出现内容漂移。本轮改为“非标比例下首尾帧置灰”。
- 派生尺寸只取整到 2 的倍数：能最接近预算，但 16:9 会得到 `1924×1082` 这类不眼熟的尺寸，读数需要额外解释。取 8 对齐后 16:9 仍是 1920×1080。
- 按长边档位派生：与现有“1080p / 4K”的说法接近，但竖屏 9:16 会得到长边 1920、宽 1080，与“宽度 1920”的读数习惯相反。
- 只按分辨率匹配：AI 返回的像素尺寸几乎从不等于视口尺寸，会把正常情况判成不匹配。
- 比例、分辨率、帧范围、fps 全匹配：匹配成功率最低，用户反而要手动选，等于没做自动匹配。
- 匹配为空时自动放宽宽高比差距：同一条成片在不同记录集下会选到不同目标，“匹配”的含义被悄悄改掉，行为不可预测。
- 匹配为空时直接报错：与“先合并出来，哪怕错”的取舍相反。
- 自动选最近的一条直接合并：用户很可能没注意到比例不一致，事后从成片上也看不出原因。改为显式“强制合并”。
- 在 `clip.json` 里新增 `ratio` 字段：冻结契约要升 version，功能上零收益；比例从宽高算出即可。
- 在运行期提供配置入口：决策 103 把配置作用域定在进程启动时，开运行期入口要处理并发与回滚，本轮不需要。

## 8. 风险与未决

- 像素预算只覆盖面积。平台还有 `maxBytes`、fps、时长的限制，长片段的 10-bit HEVC 可能先撞体积上限。缓解：vrgen 的 `plan_video` 在提交前会按预算缩放上传副本并给出具体超限项；本轮切分只保证面积，撞到体积上限时先降低 `viewport_max_pixels` 或缩短区间。
- 409600 与 2086876 按平台的 `refVideoValidator`（输入素材）理解，这是当前 `vrgen/prep/budget.py` 读取的字段。如果实测发现这两个数是输出档的限制，预算的语义要改成“按输出上限派生”，配置键与算法不变，改的是取值来源与文案。
- “智能比例”下平台返回的比例可能不等于输入比例。匹配会把它归到最近的一条记录；归不上时走“强制合并”。真实返回行为尚未实测，需要一次带额度的提交确认。
- 预设比例是固定标签，`2.39:1` 对应精确有理数 `239/100`；派生后实际比例是 `2.38793`。页面同时显示“预设比例”与“实际比例”。自由框选的比例是框的像素宽高比，可能是 `2.3924` 这类非整数，同样要显示实际比例。
- 自由模式用 B 语义：框住的范围与预览覆盖一致，但输出比例是 tan 结果（16:9 框在 75° 下是 1.99:1），不是框的像素比。预设模式用 A 语义：比例精确等于预设，但左侧 footprint 的角宽高与右侧预览的像素比不同。两种模式已经分开，用户按“要标准比例”还是“要精确框选”选择。
- 极宽或极窄的比例（例如超过 32:9）短边会小到平台可能不接受。平台 `refVideoValidator` 的 `refVideoMinAspectRatio / refVideoMaxAspectRatio` 目前没有下发，切分侧只按像素上下限校验，不做边长与比例范围的第二套判断；撞到平台限制时由 `vrgen` 的提交校验报出具体项。
- 8 对齐在窄比例下可能让实际比例偏离输入比例约 0.9%（例如宽 928 时），仍在 1% 宽高比差距上限边缘。若实测发现偏离感明显，再讨论是否改成“允许宽或高不是 8 的倍数，只保证偶数”。
- 源密度低于预算时按用户要求只提示不阻断，等于放大了源片。按真实几何，4K 源上 16:9 视口只覆盖约 32 万像素，预算 207 万是它的 6.4 倍；2.39 视口约 24 万像素，预算是它的 8.4 倍。“预算高于源片”因此是常态而不是偶发冲突。是否把选区页的提示降级成中性读数、把“低像素成片合到高像素源片”的提示改到合并侧，需要你定；当前原型把它画成中性读数。
- 首尾帧的比例表来自图片模型详情，模型详情的缓存 24 小时过期；读不到时用平台公开的八种比例兜底，可能与真实能力有偏差。
- 原型已经给出三个默认形态：`near` 列表放 3 条、“强制合并”放在每条行内、切换提示放在列表下方。它们仍是待评审项，评审后以定稿为准。
